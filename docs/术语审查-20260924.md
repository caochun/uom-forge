# 术语审查（2026-09-24）

对当前工作流使用的业务术语做一次语义核查：这些词各自指什么、是否有既有定义可依、彼此是否冲突。核查对象是当前代码与文档，方法上参照概念建模与术语学的经典判据（ORM/SBVR 的事实与约束、ISO 704/1087 的定义规则、Wand–Weber 的构件缺陷、Jackson 的领域性质与需求之分）。

**结论摘要：这套词汇分三档。**

| 档次 | 词汇 | 判断 |
| --- | --- | --- |
| 可操作，保留原样 | 实际发生/拟议安排/临时计算结果；原文明确/上下文解释/仍未确定；未决边界 | 定义清晰、可反驳、有文献实指（见第四节） |
| 有实指但换了名，需就地定义 | 业务依据、业务过程、只读能力 | 均非标准术语，各有文献对应；须各补一句内涵定义。只读能力还需统一枚举，业务过程需与"五要素"口径对齐（见 2.4、2.5、2.6） |
| 需修订 | 业务事实、检验情形、业务故事、业务对象/对象、缺口族 | 定义过宽、缺属概念、名不对实、同概念多名，或与既有术语冲突（见 2.1–2.3、2.7、第三节） |

## 一、最重要的发现：这些词曾经是类型，现在只是小标题

重构 `0bdd6d1` 之前，这些概念在 `shared/semantic.ts` 中有正式类型：

```ts
export type FactKind = 'static' | 'event' | 'state' | 'constraint' | 'role'
export type FactCertainty = 'explicit' | 'confirmed' | 'uncertain'

export interface BusinessFact {
  id: string; statement: string; kind: FactKind
  actors: string[]; objects: string[]; conditions: string[]
  result?: string; source: string; certainty: FactCertainty
}
export interface StoryStep {
  order: number; actor: string; action: string; object: string
  condition?: string; result?: string; factIds: string[]
}
export interface BusinessStory {
  id: string; name: string; goal: string; steps: StoryStep[]; factIds: string[]
}
export interface BusinessScenario {
  id: string; factIds: string[]; statement: string
  scenario: string; distinction: string
}

export interface ElementMapping {
  factId: string
  elementIds: string[]
  mappingType: 'object' | 'relation' | 'action' | 'function' | 'rule' | 'activity'
  explanation: string
  coverage: 'full' | 'partial' | 'missing'
}

export interface SemanticPlanV2 {
  schemaVersion: '2'
  status: 'facts' | 'stories' | 'mapped'
  facts: BusinessFact[]
  stories: BusinessStory[]
  mappings: ElementMapping[]
  boundaries: string[]
  clarifications: BusinessClarification[]
  scenarios?: BusinessScenario[]
}
```

（`shared/semantic.ts` 共 8 个导出，已全部列出。注意 `ElementMapping.coverage` 是 `full | partial | missing`——与现在的 `Requirement.status`、`SupportStatus` 并列，历史上曾有**三套**同义的三值状态枚举，现在剩下两套，见第三节。）

配套还有 `shared/semantic-validation.ts` 逐项校验（事实必须带 `source` 且 `containsBasis` 命中依据、`kind` 与 `certainty` 必须在枚举内、故事步骤 `order` 不得重复、故事引用的 `factId` 必须存在），以及 `server/stages/understanding-review.ts` 的逐块覆盖协议（每个原文块返回 `complete/partial/uncovered`）。

**这些词并非没有定义——定义写在一份已从工作树删除的文档里。**`README.md` 把 `docs/semantic-handoff.md` 标为"语义交接规范"（`docs/semantic-handoff.md`，工作树已无，`HEAD` 可取回），并以它作为核心问题与"不生成固定 facts/stories JSON"的依据。该文件在工作树中已不存在，但在 `HEAD` 中仍完整，且正是它给出了这三个词当时的正式表述（`HEAD:docs/semantic-handoff.md:15`）：

> 一次调用从当前文档整理稿提炼事实、业务故事、规则和少量检验情形，直接输出 Markdown。不生成固定 facts/stories JSON，不要求事实类型枚举、稳定编号、步骤顺序字段或交叉引用协议，也不对中间内容做校验重试。

同一份文档还写明"它是完整的建模业务输入，不能只是一份有损摘要"（同文件 :17；原文用"它"指代业务依据，此处照录）。所以 §1 的判断不是"定义丢了"，而是**去类型化是当时明写的决定（理由是免去校验与重试），但承载该决定的文档已不可达，README 仍在引用它**——新读者无从读到这句。

**这些词还曾经是持久化字段和界面标签。**重构前的草稿把三者整体存进本地草稿——`Project.semantic?: SemanticPlanV2`（旧 `src/types.ts:48`），恢复时经 `validateSemanticPlan` 校验（旧 `src/persistence.ts:215-233`）。界面侧同样直接呈现：`src/components/SemanticEvidence.tsx` 以 `['facts', '业务事实', facts.length]`、`['stories', '业务故事', stories.length]` 作为页签标签，正文写"运行建模后，提取出的业务事实和业务故事会先出现在这里"，并提供"搜索业务事实"输入框；该组件在旧 `WorkbenchViews.tsx:327` 被实际挂载，`ExpressionReview.tsx` 在 :395 同样挂载。两者本次重构均已删除，当前界面里 `业务事实`／`业务故事` 的命中为 **0**。

需要说明的是，旧版的页面结构（`PAGES`）与今天完全相同——业务文档／业务理解／建模／模型检验四页。事实与故事不是独立页面，而是"建模"页 `evidence` 页签的内容；这个页签本身保留至今，只是内容从"事实与故事"换成了"业务依据"。

旧草稿里的 `semantic` 负载也仍被静默带过。新旧草稿都声明 `version: 4`（旧 `src/types.ts:69`，新 `src/types.ts:82`），而恢复时的版本闸门只比较这一个数字（`persistence.ts:259`）；`readPlan` 又用 `...rest` 展开所有未识别的键（`persistence.ts:183-186`）。于是重构前保存的草稿能通过版本检查，其中的 `semantic` 会原样留在恢复后的 `plan` 上——**不被解释，也不被清除**。已删文档所称"旧版结构化事实、故事和映射数据不会被重新解释"字面成立，代价是草稿版本号没有随这次破坏性改动递增。


**这是主动的取舍，不是遗漏。**理由在 [软方法学](软方法学：从业务事实到候选模型.md) 与实验记录（`docs/Pi Agent提示词与调用精简验证.md`，已从工作树删除，可从 `HEAD` 取回）里：旧的逐条事实映射被删是为了省 token，而 `measure-workflow` 的实测结论是输入 token 降 41%、正文输出反涨 7%、端到端 665.2 秒变 714.5 秒（该实验测的是重构前的链路，对新链路只作类比，不是实测）。**省下的可评价性没有换回速度**，这是本轮核查里最值得重新权衡的一处。

## 二、逐词判定

### 2.1 检验情形——最该修的一个

定义（`prompts.ts:83`）：

> 检验情形是用于判断模型表达能力的具体案例。它从事实或故事中来，说明模型需要表达什么，以及哪些业务上不同的情形必须区分。

问题两条：

1. **这是目的定义，不是内涵定义。**说了它用来干什么，没说它是什么。ISO 704 要求属概念加种差（`X 是一种 Y，其 Z`）；Carroll 对 scenario 的定义有属（"活动的具体描述"），这里没有属。按 ISO 704 的替换原则检验，把"检验情形"换成这句定义会在语义上丢东西。
2. **没有稳定 ID，所以"逐一沿用"不可验证。**提示词要求"明确标出这些情形，后续设计和检查逐一沿用，不重新猜测"，但旧版是**程序钉住**的，不只是携带字段：表达检查的用例直接由 `result.semantic.scenarios` 生成（`0bdd6d1^:server/stages/expression.ts:106-111` 取 `id`、`statement`、`scenario`、`distinction`、`factIds` 组成检查基线），且 `0bdd6d1^:server/validation/expression.ts` 会拒绝任何改写了 `fact` 或 `scenario` 原文的判断（同文件 :220）——即模型无法通过改写情形来制造"通过"。现在这套机制不存在，只能靠 LLM 自觉，程序无法核验。

**与业务语汇不对齐（反向信号）。**业务文档 `高压接入方案业务规则说明1.docx` 用的是**场景**，共 7 处，全部指向业务分支而非检验案例：

```
（一）新装场景 / （二）增容场景
单电源场景下选取不同线路中距离最近的接入点
双电源场景下选择来自不同线路且距离最近的电源接入点
双回路场景下同样选取不同线路且距离最近的电源接入点
若为单电源增容场景，仅评估原电源接入方案可行性
对于单电源增容升级为双电源的场景，一路保持采用原电源接入点
```

工具用"情形"避开域名措辞是对的（否则与业务自己的"场景"混淆），但代价是术语与业务语汇不对齐，不能指望领域专家一眼认出。同一文档中 `事实`/`故事`/`情形` 出现次数均为 **0**。

### 2.2 业务事实——过宽，且与多个既有概念冲突

定义（`prompts.ts:67`）：

> 每项事实表示一条模型必须保留的业务判断，可以是静态状态、业务联系、约束，也可以是一次变化及其结果。

问题三条：

1. **把 ORM 明确分家的三类压进一个词。**ORM 的概念模式含三种不同内容：基础事实类型（fact types）、约束（constraints）、推导规则（derivation rules）。约束不是事实，推导规则描述派生事实如何计算，二者都不是 fact type。这里"约束"被吸收进"事实"。ORM 对此有硬判据（n 元事实表最短唯一约束测长 n−1），这里没有。
2. **"business fact"不是术语。**SBVR 的术语是 `fact type`（其定义本身在 `SBVR_-59` 中被重新谈判过）；Ross 明确反对对业务方用 fact / fact type，主张 `concept model` / `verb concept`；BRG 与 SBVR 都未规范 "business fact"。中文最接近的学理源头是 Ross《业务规则方法原理》中译本第五章"组织基本的业务知识——关于术语和事实"（英文用 fact / fact model）——该措辞出自中译本，不是国标术语。
3. **与中文标准与数据仓库双重撞词。**GB/T 11457-2006 无"事实"条目；"事实"只出现在"数据"条目的定义正文中（条目 2.387，此处为释义不是逐字：数据是事实、概念或指令的表示，1995 版对应条目 2.119）；而数据仓库语境里"事实"（fact）指**可度量的业务事件数值**，与这里的含义完全不同。

### 2.3 业务故事——名不对实

定义（`prompts.ts:72`）：

> 业务故事表示围绕同一事项、参与者或结果展开的连续业务过程。对每个重要过程说明目标、参与者、涉及事项、必要步骤、分支和结果……

问题三条：

1. **中文标准译名是"用户故事"（user story），"业务故事"不是通用术语。**文献中"业务故事"只在拆分复杂故事时指需求部分这一窄用法里出现。
2. **实际语义是"用例"或 domain story，不是 user story。**Cockburn 的用例包含目标、参与者、主成功场景与扩展分支，正对应这里的描述；Beck 的 user story 是卡片、承诺对话、可测试，刻意省略分支与前置条件。Domain Storytelling 的 domain story 是 actor–activity–workobject 的编号序列，但**刻意排除** if 分支——这里却要求写分支。
3. **循环定义风险。**"连续业务过程"里的"业务过程"同时是一个元素类型（`activities`），用元素类型定义另一个概念，两者关系需要显式说明。

补充：正反定义已经写过，就在同一份提示词里——"事实是需要保留的单条判断，故事是这些判断在一个过程中的组织"（`prompts.ts:73`）。这句质量很高，但与"连续业务过程"那句并列出现，二者对"故事"的界定口径不同：一句说它是判断的组织，另一句说它是连续过程。需要择一为准。

### 2.4 只读能力——枚举在漂，且与阶段名撞词

| 出处 | 枚举 |
| --- | --- |
| `prompts.ts:122` | 查询、计算、**设计、模拟**、校核或评估 |
| [软方法学](软方法学：从业务事实到候选模型.md):58 | 查询、计算、校核和**推荐** |

两份清单不一致：提示词有"设计""模拟"，文档有"推荐"；两侧都不完整。模型读前者、人读后者，长期必然分叉。

两个结构问题：

1. **枚举式定义。**ISO 704 指出枚举定义只适用于有限且封闭的集合，而这里明显开放（"推荐""预测"都该进）。
2. **与阶段名撞词。**"设计"作为只读能力，与阶段名"模型设计"同形；[提示词审查](提示词审查-20260924.md)已建议改写为"方案设计"。高压接入场景里"设计"正是核心动词（设计院出接入方案），不能删。

领域语汇支持"推荐"留在清单里：`高压接入方案业务规则说明1.docx` 用词统计为 评分 13、推荐 7、查询 4、计算 4、校核 1，而 阈值 0。即业务自己最常用的只读动作是**推荐**和**评分**，提示词恰好漏掉"推荐"而保留了业务几乎不用的"模拟"。

概念支柱本身是好的：Meyer 的命令查询分离（"提问不应改变答案"），查询有返回值无副作用。这比经典 RDD 走得更远——把只读能力升为一等元素，贴合方案设计、模拟、校核类业务。

### 2.5 业务过程——第几个要素？

任务书两次提到"五要素模型"，但**从未列举**是哪五个。而 `CORE_QUESTION`（`methodology.ts:1`）正好只列五个：

> 当前的对象、关系、业务操作、只读能力和规则，能不能表达一个具体的业务事实或业务过程？

`MODEL_COLLECTIONS`（`shared/model.ts:72`）却是**六个**：objects、relations、actions、functions、rules、activities。业务过程遍布 `CORE_QUESTION` 的宾语、编译契约、`normalizeModelPlan` 的分节、评估阶段主循环和界面，却不在那个核心问题的主语名单里。

三种可能：核心问题是旧版五要素遗留、业务过程是未获承认的第六要素、或"五要素"本就是过时命名。无论哪种，**任务书、核心问题、模式三处不一致**是事实。

术语选择本身是有辨识力的：中文文献区分"业务过程"（更一般化、学术与标准语境）与"业务流程"（更具体、实务口语），标准用法中的"过程—活动—任务"层级（ISO 9000 / BPMN / SPEM）里，`activities` 对应的是流程中的活动集合。选"业务过程"偏学术是正确的，但中文实务界更常用"业务流程"，与业务方沟通会有摩擦。

### 2.6 业务依据——不是标准术语，但定位站得住

查证：**不是标准术语**。GB/T 45802-2025《系统与软件工程 生存周期过程 需求工程》（等同采用 ISO/IEC/IEEE 29148:2018）的第 3 章术语中没有此条目；IREB CPRE 术语表（中文版 V2.0）也没有。最接近的规范词是**需求来源（Requirement Source）**。

仓库内同样没有内涵定义。唯一接近定义的一句在 `prompts.ts:110`——"业务依据是本轮设计和表达检查共同使用的业务输入"。它说明这份文本被谁读取，不说明它是什么，与 2.1 对"检验情形"的批评同属一类：有角色说明，缺属概念加种差。

但功能定位有依据，对应文献中两个明确的实指：

- **Jackson 的领域性质（domain properties）**：indicative 的、描述世界本来如何的陈述，与 optative 的需求、machine specification 分列。Jackson 的健全性条件 `machine spec ∧ domain properties ⇒ requirement` 可直接套到"整理稿/业务依据 → 模型设计"的分野上。
- **Ross 的事实模型（fact model）**：结构化业务词汇，名词（terms）与动词（wordings），业务规则直接建在其上——对应源码原句"后续设计和检查只读取本份依据"。

所以它是自造词，但自造得有依据。风险在于无出处声明，容易被误认为既有概念。

### 2.7 业务对象 / 对象——构件冗余

类型名是 `objects`，中文标签在 UI 上是"对象"（`ModelElementPreview.tsx:12`）或"对象关系"（`WorkbenchViews.tsx:218`），而文档与提示词里另有"业务对象"（4 处，含 README）。同一概念两个名字。另有标签与计数不一致：页签文案取自 `COLLECTIONS` 的 `['objects', '对象关系']`，而计数取自 `model[id].length`，即只数 `objects`；该页签内实际渲染的是 `ModelGraph`（对象与关系都画）加一个只列对象的索引。于是"对象关系 5"这个词同时说了三件事：名字指两个集合、数字只数一个集合、画面呈现两个集合。用户无法从文案判断 5 是对象数还是关系数。

## 三、构件层面的缺陷（Wand–Weber 四类）

用信息系统的本体论评价框架看，当前词汇有四处可指认的缺陷。其中 `模型` 一词两义、只读能力中"设计"与阶段名撞词、"本体"漂移三项，已由 [提示词审查](提示词审查-20260924.md) §9 的第 3、4、6 条单独提出；本节按构件缺陷归类，并补上该表未覆盖的两项——构件冗余（同一概念多种词形）与构件缺失（有概念无词形）。需要说明两处分寸差异，以免与本目录下另一份报告读起来像互相矛盾：[提示词审查](提示词审查-20260924.md) §9 的"术语资产……在八个阶段间保持一致"，衡量的是**同一个词在各阶段之间指向是否稳定**；本节的构件冗余与缺失，衡量的是**同一个概念是否只有一个词形**。前者成立不蕴含后者，两份结论并不冲突——同一份提示词可以做到"阶段之间用词统一"，同时仍存在"一个概念多种写法"和"有概念无专名"。

**构件过载（一个词形承载多个本体概念）**

- `模型`：一行之内两义——"每次**模型**调用"指语言模型，"输入材料和**模型**都只是数据"指候选模型。[提示词审查](提示词审查-20260924.md)已抓，建议语言模型侧改"语言模型"或"推理调用"。
- `对象`：既指业务对象（`objects` 集合），又指关系端点、操作作用对象、只读能力所需对象。
- `业务事实`：见 2.2，同时承载事实、约束、变化结果。

**构件冗余（多个词形映射同一本体概念）**

- 状态枚举：`Requirement.status: 'covered' | 'partial' | 'missing'`（`shared/model.ts:48`）与 `SupportStatus: 'supported' | 'partial' | 'missing'`（`shared/analysis.ts:27`）——同一个三值概念，两套枚举，`covered` 与 `supported` 语义相同。重构前还有第三套 `ElementMapping.coverage: 'full' | 'partial' | 'missing'`（`shared/semantic.ts`），说明同一个三值语义被**独立引入**过三次而没有统一（不是先后改名，而是各自发明）。`covered` 现在是**不可达的兼容值**：schema 仍允许它（`model-schema.ts:62`），校验器仍检查它（`model.ts:40`），旧草稿仍会读它（`persistence.ts:107`），但编译器永不可能产生它——`validateCompiledModel` 要求每条 requirement 恰好是 `partial`（`compiled-model.ts:52-57`）。它只能从历史草稿进入，却被新代码的校验路径完整保留。
- 缺口族：共 **八个在用词形**指同一个概念（另有 1 个建议名，见本条末），是本节最严重的一处冗余。基础两个——`缺口`（56 处）、`缺陷`（12 处）；带修饰的四个——`表达缺口`（`methodology.ts:19`、`软方法学:88`、`提示词审查:518`）、`模型缺口`（`methodology.ts:53`、`design-review.ts:38,56`、`assessment.ts:18`、`BusinessProcessSupport.tsx:382`）、`模型缺陷`（`methodology.ts:20,49`）、`语义缺口`（`BusinessProcessSupport.tsx:274` 的界面文案"此项未发现语义缺口"）；把"本体"写进词形的两个——`本体缺口`（`assessment.ts:25`）、`本体语义缺口`（`assessment.ts:13`）。各词形的计数互相嵌套（`本体语义缺口` 计入 `语义缺口`，后者又计入 `缺口`），因此不可相加。[提示词审查](提示词审查-20260924.md) 建议统一改用 `模型语义缺口`，该名尚未落地，不计入在用词形。`assessment.ts:13,25` 两处是全库提示词层出现"本体"的全部位置（其余一律用"模型/业务表达"），属术语漂移；而界面已经用了裸 `语义缺口`，说明这个词形已进入用户可见文案，不只是提示词内部问题。
- `情形` / `检验情形` / `场景`：这三个词形不构成同义冗余，需要分开说。`场景` 21 处**没有一处**是 `检验情形` 的同义词——任务书"示范场景"14、提示词"未提出的场景"3（含两处引文）、业务个案"高压接入场景"2、NeOn"场景化"1、以及 [软方法学](软方法学：从业务事实到候选模型.md):78 的一处对举。真正的问题是裸用 `情形`（99 处；`情形` 全库 151 处，其中 52 处是"检验情形"）兼两义：绝大多数是 `检验情形` 的简写或回指（"受影响的情形""失败情形""具体情形""这些情形"），少数是泛指的"情况"——实测至少一处，`methodology.ts:57` 的"需要重新理解文档或请用户补充的情形保留为未决"。同一词形承担"检验案例"与"一般情况"，于是两句真实要求之间没有共同指称：`prompts.ts:84` 说"明确标出这些情形，后续设计和检查逐一沿用"，`design-review.ts:12` 说"业务依据已经列出的检验情形必须逐一检查"——前者标出的是依据里写下的那批，后者要检查的是依据里列出的那批，而"这些情形"在两处都靠裸 `情形` 指代，模型既可能理解为"依据已列出的"，也可能理解为"手头这几条"。
- `业务对象` / `对象`：同一概念两个词形（`objects` 集合的中文名，UI 用"对象"、文档用"业务对象"），详见 2.7。该条目还牵出一处标签缺陷——"对象关系"页签的名字指两个集合、数字只数一个，属于命名与计数不对应，严格说超出术语范围，但根因是同一概念没有单一词形。

**构件缺失（有本体概念但无词形）**

- **状态**：方法论反复出现"改变对象、关系或状态"，但元素类型里没有状态，只能落在描述文本里。
- **参与者/角色**：同上，`StoryStep` 曾有 `actor` 字段，现在没有承载。
- **约束**：被吸收进"业务事实"和"业务规则"，无独立承载。

**同概念多词形的代价**由解析器的容错逻辑直接体现。提示词的首行协议只要求三种写法，而 `designVerdict`（`design-review.ts:55-57`）为判定同一件事必须接受 13 种：

| 结论 | 解析器接受的写法 |
| --- | --- |
| `sufficient`（可表达） | 可表达 / 表达充分 / 可以表达 |
| `revise`（需修改） | 需修改 / 需要修改 / 存在缺口 / 表达不足 / 无法表达 / 模型缺口 |
| `clarify`（业务待澄清） | 业务待澄清 / 待澄清 / 需要业务澄清 / 需业务澄清 |

判定前还会剥掉 `#*`>[]【】` 等装饰字符。同义表是协议本身的三倍多（13 / 3）——这是同一概念没有单一词形的直接代价：多出来的写法全部由程序兜底。

## 四、最值钱的部分：两组三分法

这两组是全套词汇里质量最高的，定义可操作、可反驳、有文献实指：

**实际发生的事实 / 拟议安排 / 临时计算结果**（`prompts.ts:68`）

对应 BWW 的状态与事件之分、UFO 的 type/instance/relator 之分。高压接入场景里"方案（拟议实例）、接入事项（实际发生）、计算结果（临时）"正好是这三类，而这是该领域最容易混淆的地方。

**原文明确的事实 / 根据上下文得到的解释 / 仍未确定的信息**（`prompts.ts:69`）

对应认识论上的断言强度分级。配合同一条里的"解释不能写成硬性要求"，封住了 LLM 最常见的失败模式：把推断当事实输出。

以及 **未决边界**——"业务本身没有答案时保留边界……把边界写在受影响的定义中，不靠末尾免责声明掩盖设计中的假设"（`methodology.ts:20`）。这条抓的是隐蔽的失败模式（自相矛盾而非凭空捏造），比"不要编造"难得多。

**建议：这三组原样保留，其余术语向它们看齐。**

## 五、建议（按优先级）

1. **给检验情形发稳定 ID 并写回业务依据**，让"后续设计和检查逐一沿用"（`prompts.ts:84`）可核对。这是可验证性问题，不是措辞问题；旧版不止有 `BusinessScenario` 的 ID 与 `factIds`，还有一整套钉住机制（检查用例由情形生成、判断不得改写情形原文，见 2.1），可直接参照恢复。
2. **消掉缺口族与两套状态枚举**，成本近零、纯收益。缺口族保留一个最强表述（建议"表达缺口"），其余引用式带过；`covered` 改为 `supported`（它现在只是历史草稿的兼容值，新编译不可能产生，见第三节）。
3. **对齐"五要素"：**统一任务书、`CORE_QUESTION` 与六个集合的表述，或在文档中显式说明业务过程为何是第六要素。
4. **为每个保留术语补一句内涵定义**（属概念 + 种差），别让它们只以小标题形式存在于提示词里。项目已有这个先例：[任务书解读](任务书技术核心与智能体平台架构解读.md) 开篇就声明"可操作本体"是项目叙事和工程用语、"目前国际研究中没有一个与之完全对应、定义统一的单一术语"——中央术语标注自造反而使文档更可信，这批词是漏了这一步，不是坏在自造。最缺的是"检验情形"和"业务事实"。"业务故事"若保留，需说明它与"用例""用户故事"的区别，并解决与"业务过程"的循环定义。
5. **统一只读能力的枚举**，取"查询、计算、模拟、校核、评估、推荐"这类开放词的并集，或改为内涵定义加举例。同时把"设计"改为"方案设计"消歧。
6. **消 `模型` 一词两义**：语言模型侧统一写"语言模型"或"推理调用"。
7. **消除 `业务对象` / `对象` 的冗余**，并修正"对象关系"页签把两个集合压进一个标签的问题。

## 六、权重说明

需要说明的是，以上判定按**工程可用性**而非纯术语学标准给出。若按 ISO 704 严格判，业务依据与只读能力（以及"需修订"一档的多数词）都属"自造词或定义不合规"，应当逐一给出定义或替换；但本项目是内部工具，术语的主要读者是提示词里的模型与审阅的领域专家，不是标准委员会。因此本报告只对**确实影响正确性或可验证性**的"需修订"一档（业务事实、检验情形、业务故事、业务对象/对象、缺口族）主张修改，对应第五节第 1、2、4、7 条；其余列为建议。

术语本身不是问题，术语与产物不匹配才是问题：这些词曾经是类型，现在只是小标题，而提示词仍按"它们是类型"的语气要求模型逐一沿用、明确标出、不得混淆。要么把类型加回来，要么把语气改过来——**当前状态是两者都不彻底**。

**事实与约束的区分**

- Halpin, T. *Object-Role Modeling: Principles and Benefits*；概念模式含基础事实类型、约束与推导规则三类内容。事实类型的中文译法（"事实类型"，区分 fact 与 fact type）见施伯乐等译《信息建模与关系数据库》。
- OMG. *Semantics of Business Vocabulary and Business Rules (SBVR)*, formal/13-09-05. `fact` 定义为"proposition taken to be true by the business"，`fact type` 为逻辑化类型；定义争议见 OMG issue [SBVR_-59](https://issues.omg.org/issues/SBVR_-59)（Barkmeyer, 2006）。
- Ross, R. G. *Concept Model vs. Fact Model vs. Conceptual Data Model*，[Business Rules Journal 13(1), 2012](https://www.brcommunity.com/articles.php?id=b632)——主张对业务方改用 concept model / verb concept。
- Business Rules Group, *Defining Business Rules ~ What Are They Really?*（1995；2000 最终报告）。业务规则定义"a statement that defines or constrains some aspect of the business"，SBVR 后收窄为"a rule that is under business jurisdiction"。

**用例、场景与故事**

- Carroll, J. M. (ed.) *Scenario-Based Design*, Wiley, 1995——scenario 为"a concrete description of activity that the user engages in when performing a specific task"。
- Cockburn, A. *Writing Effective Use Cases*——用例为契约，主成功场景与扩展分支；scenario 的定义在文献中并不统一（Sutcliffe 语："被太多作者劫持"）。
- Beck, K. *Extreme Programming Explained*（1999）与 Beck & Fowler *Planning Extreme Programming*（2000）——user story 为卡片、承诺对话、可测试，刻意省略分支。中文标准译名为"用户故事"。

**过程与活动**

- ISO 9000:2005 §3.4.1：process 为"set of interrelated or interacting activities which transforms inputs into outputs"；ISO/IEC/IEEE 24765 沿用并给出 activity 为"a set of cohesive tasks of a process"。BPMN 2.0 中 Activity 为通用词，Task 为原子活动，Sub-Process 为复合活动。

**能力**

- TOGAF 与 Open Group G161 将 capability 定义为"the ability to do something"，强调"做什么"而非"怎么做"；中文语境经 MODAF → TOGAF → OMG BAWG 引入。

**术语学规则**

- ISO 704（2009/2022）*Terminology work — Principles and methods* 与 ISO 1087。内含定义要求属概念加种差，优先于枚举定义；替换原则要求"以定义替换术语不得丢失含义"；单义性（monosemy）与单名性（mononymy）要求一词一概念、一概念一词；须避免循环定义、不完整定义与否定定义。

**构件缺陷判据**
