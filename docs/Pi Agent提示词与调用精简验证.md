# Pi Agent 提示词与调用精简验证

> 本文记录的是 2026-09-20 较早一轮“保留结构化语义准备”的实验。之后默认流程已简化为业务理解 → 文本业务依据 → 模型设计 → JSON；本文耗时与调用数不能作为新流程的实测结果。当前流程见 [语义交接规范](semantic-handoff.md)。

## 改动范围

目标是减少重复输入、重复生成与串行交接，保持业务条件、引用和独立核对。没有更换模型、修改 `.env` 的推理级别或提高应用默认超时，也没有新增业务理解生成阶段。

- 业务理解使用 7 个章节，合并原先分散的身份、状态变化与只读能力说明，不在此阶段要求对象拆分、合并决策，不再重复生成代表性事实清单。
- 故事组织、建模和映射接收事实的语义字段，去掉重复的 `source` 引文。故事保留全部步骤及条件、结果；故事级额外引用保留为 `contextFactIds`。原始事实、引文和引用关系继续保存在语义草稿中。
- 建模仍保留一份完整业务说明，防止尚未提取的业务范围、例外或用户确认消失。建模说明只输出模型定义和必要理由，不复述完整故事。
- Pi 直接输出建模 Markdown，由宿主解析澄清并交给编译；不使用全文 `finish` 工具或编译前的可选独立检查。编译后的实际候选继续接受业务表达检查和必要的局部修正。
- 编译只接收建模说明。事实、故事和理解检查元数据由宿主持有，传给后续检查和映射。固定的空证据、空属性、空输入及待评估标记由已有程序补齐，提示词要求省略这些重复输出。
- 业务理解的语义修正返回段落替换，程序对同一版草稿唯一匹配并原子应用。无效定位、重叠、未知原文引用或必要章节被删除时保留草稿；修订后的说明标为未再次独立核对。格式补全仍可能生成全文，但与语义修正共享最多两次 Agent 生成预算。
- 完整 JSON 后单独成行的残缺 Markdown 结束围栏由程序清理；不修补损坏的 JSON，不移除业务文本，不放宽字段和引用校验。

## 实验方法

输入为项目根目录的 `高压接入方案业务规则说明1.docx`。Mammoth 转换后，在浏览器中执行实际前端 `documentToBlocks`，得到 57 个顶层块、3,578 个正文字符。旧诊断脚本提取了表格内部段落，产生 115 个块，不能直接作为本轮对照。

基线是本轮改动前的工作区快照，已经包含上一轮“只输出 gaps、取消业务理解 finish”的改动，并非 Git HEAD。新版也冻结快照。两者顺序运行，使用同一份 blocks、GLM `glm-5.3-flash`、Coding Plan endpoint、`reasoning_effort=low`、`max_tokens=32768`，其余采样设置相同。实验单请求及 Pi 阶段时限统一为 600 秒；项目默认的 300 秒未修改。

`low` 仅为本次受控实验参数，不能代表 `.env` 中 `max` 的生产耗时。顺序运行避免同时竞争请求配额，但服务负载、缓存和生成随机性仍可能不同。单次对比不提供稳定的延迟分位数或质量统计结论。

新增 `scripts/measure-workflow.ts` 在导入两个调用路径之前安装 HTTP 观测，同时覆盖 Pi SDK 与普通 provider。记录每次请求的输入字符数、正文/工具参数字符数、思考字符数、上游返回的 token usage、缓存 token、首段正文时间及总耗时。输出和冻结源码保存在应用仓库之外；不保存请求头或 API key。

实验覆盖业务理解、事实、故事、建模、编译、表达检查/修正和事实映射。没有包含用户等待确认的时间，也没有执行模型自述和最终支撑评估。

复现方式（输入为按前端分块后的 JSON）：

```sh
npx tsx scripts/measure-workflow.ts --input /path/to/document.json --output /path/to/new-results --source-root /path/to/frozen-checkout --effort low
```

本轮原始记录与源码快照目录：`/Users/chun/Downloads/uom-forge-evaluation/prompt-latency-2026-09-20/`。其中 `baseline/` 是被中断的不完整启动，不用于比较；完整基线使用 `baseline-2/`。`candidate/` 是发现标题冒号误判后保留的失败记录；修复后重新冻结代码，完整新版使用 `candidate-final/`。

## 固定输入的大小比较

下表使用基线高压文档产出的同一份理解、39 项事实、1 个故事、8 个情形，仅比较代码投影前后的输入，不混入不同生成结果的差异。这里是字符数，不是 token 或耗时。

| 输入 | 修改前字符 | 修改后字符 | 减少 |
| --- | ---: | ---: | ---: |
| 建模提示词，业务说明及语义准备相同 | 32,518 | 23,632 | 27.3% |
| 故事组织的事实数据 | 15,707 | 7,022 | 55.3% |
| 映射的事实与故事数据 | 19,135 | 10,165 | 46.9% |
| 编译提示词，建模说明相同 | 28,883 | 6,397 | 77.9% |

另用此前保存的 DOMSYS H2S 结果（28 项事实、1 个故事）验证投影与业务无关：相同输入的建模提示词减少 19.1%，编译提示词减少约 58.5%。这里只复用已有结果衡量体积，没有把该案例写入产品提示词，也没有重新评测该案例的模型质量。

## 真实运行与语义复核

**本轮输入明显缩小，但完整实测没有提速：665.2 秒 → 714.5 秒，增加约 7.4%。** 不能据此把压缩输入当作端到端加速的充分条件。

| 阶段 | 基线请求数 / 秒 | 新版请求数 / 秒 |
| --- | ---: | ---: |
| 业务理解、独立核对及必要修正 | 3 / 239.8 | 2 / 136.3 |
| 事实提取 | 1 / 70.5 | 2 / 189.6 |
| 故事与代表性情形 | 1 / 53.4 | 1 / 75.1 |
| 建模说明 | 1 / 75.1 | 1 / 92.2 |
| 编译 | 1 / 78.3 | 1 / 96.6 |
| 表达检查 | 2 / 88.4 | 1 / 67.8 |
| 事实映射 | 1 / 59.4 | 1 / 56.4 |
| 整体（含宿主处理） | **10 / 665.2** | **9 / 714.5** |

业务理解本轮减少了一次修正，因为新版独立核对返回空 gaps；这不是确定性的省略规则，不能保证每次都少一个调用。基线建模也直接调用 finish，没有触发额外交接重试，因此本轮建模实际请求数没有减少。新版编译在约 1.5 秒开始输出正文，基线约 27.3 秒；但总生成耗时增加。新版事实多出一次纯格式重试，已由本轮最后的围栏清理修复，详见下文。

| 总量（上游 usage） | 基线 | 新版 |
| --- | ---: | ---: |
| 输入 token，含缓存 | 113,752 | 67,127 |
| 正文/工具参数输出 token，不含思考 | 30,205 | 32,320 |
| 思考 token | 2,881 | 577 |
| 命中缓存 token | 23,616 | 0 |
| 提取的事实 | 39 | 57 |
| 业务故事 | 1 | 4 |
| 代表性情形 | 8 | 7 |
| 候选模型元素 | 44 | 53 |

输入 token 减少约 41%，正文输出反而增加约 7%。两轮事实、故事及模型规模不同，缓存命中也不同；这些因素限制了单次耗时比较的解释范围。编译的输入 token 从 15,314 降到 4,278，但正文输出从 3,422 增到 3,802，总耗时增加，说明后续不能仅看输入长度。

两轮均完成事实映射，自动表达检查分别对本轮 8 个、7 个情形返回通过。映射条目分别为 44、89 条（同一事实可以对应多个元素类型，不等于事实数），两轮各有 2 条 missing；映射完成不代表全部事实充分表达。新版另有一条引用无效的澄清被隔离，模型及其他有效结果保留。

### 人工核对的业务边界

以下直接检查实际候选定义，而非根据元素数量判断质量；未使用专家参考模型。

| 核对点 | 基线 | 新版 |
| --- | --- | --- |
| 10kV、总容量≤20000kVA | 保留 | 保留 |
| 五项基础筛选，以及筛选＜80%与割接后≤80%的区别 | 保留 | 保留 |
| 同站双电源须来自不同电源进线的两段母线 | 候选仅写同站两段母线，遗漏进线限定 | 保留进线限定 |
| 扩散半径及5条不同线路 | 查询定义未明确完整数值序列和数量 | 保留200/500/800/1000米及5条线路 |
| 新出线五类触发、1000米割接搜索条件、15公里上限 | 保留 | 保留 |
| 单电源增容仅评估原点；升级双电源保持原路并推荐另一路 | 过程保留 | 过程保留 |
| 负荷转移来源与接收目标的绑定 | 有显式来源与目标关系 | 明确目标，但来源如何绑定到同一次割接不够清楚，需复核 |
| 评分权重、每运行方式至少1套且总数≤10套 | 保留 | 保留 |
| 设备健康评分细节 | 候选只保留维度权重，没有完整分档 | 保留更多分档，但擅写“满分95换算15%”；原文三项最大分为30+35+25=90，且未规定归一化 |
| 施工可实施性公式写“历史停电”，明细写“负荷切割与转供”的冲突 | 未明确保留 | 未明确保留 |

因此不能宣称质量不变或模型已完整正确。新版“满分95”的错误已经出现在建模说明中，编译随后保留；它不是编译器删除事实后才产生的。两轮对施工评分冲突的遗漏都发生在业务理解，后续不读取原文的模型检查无法补回该信息。自动检查通过仅说明所选情形的判断通过，不覆盖这些人工发现的缺陷。

这轮适合确认输入投影、直接交接和机械格式处理的效果；不据此把所有阶段默认推理强度改成 low，也不把单个案例的业务词或预期模型写进提示词。后续应固定同一份语义输入重复测量生成量与耗时，并独立评估规则保真和实例绑定，避免通过减少业务内容换取更短时间。

真实运行发现两类无须重新推理的格式问题。第一类是建模标题带中文冒号，被精确标题检查误判；程序已统一规范标题，并用捕获的真实输出验证可以一次通过，修复后重新执行完整实验。第二类是完整事实 JSON 后多出一行两个反引号，导致事实整批重新生成。围栏清理是在这次冻结运行期间补入的最后一项修复，未改变运行中的代码快照。本报告保留实测中的这次重试，不从总耗时中扣除。

对 `candidate-final/003-semantic-response.txt` 做原样回放，最终代码仅调用一次提取器，即通过 JSON、56 项事实字段及全部业务说明引用校验。记录见 `fence-replay.json`；这证明该响应不需要 LLM 再生成，不能把它当成新的端到端耗时样本。
