# 软方法学：从业务事实到候选模型

## 目的

UOM Forge 的建模不是从业务文档中机械抽取名词，也不是把每个流程步骤转换成一个对象。它要形成一个足够简单、但能表达关键业务事实的候选模型，供业务人员审阅和后续过程支撑评估。

这里的“软方法学”是一组持续使用的判断原则，而不是固定的对象清单、关系清单或必须执行的问卷。它给建模者提供方向，同时允许根据不同领域的业务语义作出不同的合理设计。

## 核心问题

建模过程中始终围绕一个问题：

> 当前的对象、关系、业务操作、只读能力和规则，能不能表达一个具体的业务事实或业务过程？

例如，不只问“文档中有没有出现电源点”，还要问：

- 能否表达某一次接入事项选择了哪个电源点；
- 能否区分不同事项选择了不同电源点；
- 能否表达电源点在当前状态下是否满足容量和负载条件；
- 能否区分实际接入、拟议方案和临时查询结果；
- 能否追溯某个候选方案属于哪一次业务事项。

只有现有模型无法表达这些事实时，才考虑增加或调整模型元素。

## 建模对象的判断

对象是具有独立业务身份、需要被长期管理、能够被重复引用，或者本身是需要追踪的业务事项、记录或产出的概念。

判断一个概念是否成为对象时，依次考虑：

1. 它是否能被单独识别，而不是某个对象的描述性信息？
2. 它是否会在多次业务中被引用或持续存在？
3. 它是否需要独立追踪生命周期、状态或责任？
4. 它是否是一次业务事项、业务记录或业务产出？
5. 如果不单独建对象，现有对象、关系和规则是否仍能明确表达相关事实？

最后一个问题优先级最高。一个概念即使在文档中反复出现，也不必然需要成为对象；如果它只是属性、状态、指标、阈值、评分或计算结果，就应优先保留在对象描述、关系上下文或规则中。

同样，业务过程尚未发生，不代表其中涉及的主体、资源或业务事项没有独立身份。对象的成立依据是业务语义，而不是某个操作是否已经执行。

## 关系的判断

关系表达已经存在的业务联系，并说明联系的方向、双方和必要上下文。关系设计首先回答：

- 谁和谁发生了什么联系？
- 这条联系属于哪一次业务事项、合同、方案或其他上下文？
- 联系是长期事实、一次业务记录中的事实，还是查询或计算得到的临时结果？
- 仅通过共享一个容器，能否唯一确定双方的直接联系？

可以由已有关系路径稳定推导出的联系，不重复增加关系。反过来，如果同一批对象之间可能存在多次业务、多个角色或多种安排，就必须通过业务事项、关系上下文或其他已有语义把它们区分开。

关系不能只因为两个名词同时出现就建立。关系必须能帮助表达真实事实，例如“某次接入事项采用某方案”属于有业务上下文的事实，而“方案有评分”更可能是方案的属性或计算结果。

## 业务操作与只读能力

业务操作表示会产生副作用的行为：它创建业务对象或记录，建立或解除业务关系，或者改变对象、关系的业务状态。定义操作时要说明目标、前提和结果，区分设计、模拟、审核与实际执行。

查询、计算、校核、评估和推荐属于只读能力。它们可以返回临时结果，也可以为业务操作提供依据，但不会因为被调用就改变业务状态。

一个业务过程不自动等于一个操作。完整过程通常由若干业务操作和只读能力共同支撑；过程中的查询或评分只有在明确需要保存、追踪或形成业务记录时，才考虑作为独立对象或操作的结果。

## 规则与边界

规则应绑定到实际作用对象、操作或业务过程，保留条件、阈值、单位、公式、优先级和否决结果。不要把“有一个 80% 阈值”单独建成对象，也不要把“按规则计算”当作完整规则。

建模判断与边界用于记录：

- 为什么两个概念合并或拆分；
- 某个关系只在什么业务上下文成立；
- 哪些属性和算法本轮有意不细化；
- 哪些业务事实仍未明确；
- 哪些内容不属于当前模型范围。

边界说明不是待确认问题清单。只有当未决业务事实会实质改变对象、关系、操作、规则或过程时，才提出业务问题；是否采用某种建模方式本身不交给用户选择。

## 代表性业务情形

软方法学不要求穷举所有场景，而是选择少量最能区分模型边界的情形进行检验。代表性情形通常覆盖：

- 同一主体发生两次不同业务事项；
- 同一事项涉及多个对象或多个资源；
- 两种安排业务结果不同，但表面上使用相同对象；
- 拟议状态与实际状态不同；
- 多方以不同角色参与同一事项；
- 某个结果是持久业务记录，还是只在计算期间存在；
- 同一过程在不同条件下复用或分支。

每个情形都要能回答“模型中的哪些元素绑定了这些实例”。如果只能说“模型包含相关名词”，却无法确定实例之间的实际联系，就说明模型仍有表达缺口。

## 两条建模路线

### direct

direct 先用两个隔离调用提取业务事实、组织业务故事，再由普通模型调用完成建模说明，并由另一次调用将说明编译为 JSON。它的软方法学判断仍由建模调用负责，但输入已经带有经过程序校验的事实与故事；之后由统一的业务表达检查构造代表性情形并进行有限的定点修正。

它的优点是调用次数少、路径清晰；局限是语义建模阶段没有内置的自主循环，容易遗漏某个关键业务事实。

### Pi Agent

Pi Agent 使用同一套事实、故事和业务建模提示词，但由 Agent 自主决定是否调用独立检查。检查意见是建议，不是必须逐项消除的清单；Agent 可以根据业务依据修正，也可以保留合理的模型边界后提交。发现不同答案会改变当前模型的真实业务歧义时，Agent 通过结构化澄清工具登记依据、不同解释和模型影响。

Pi 的检查工具负责反馈可能影响核心业务表达的缺口，Pi 负责判断这些意见是否有依据。JSON 编译失败时，Pi 还可以根据程序校验错误做局部修复。无论是否使用 Pi，最终候选都会经过相同的业务表达检查和本地结构校验。

Pi 的循环只在当前阶段内保留上下文；不同阶段之间不继承隐式会话。下一阶段只接收上一阶段明确交付的输入。

## 阶段边界

Forge 将“理解业务”和“设计模型”分开：

1. 业务理解阶段阅读原始文档，形成结构清晰的业务说明，区分事实、解释和不确定事项。
2. 语义准备阶段从业务说明提取带原句依据的最小事实，并只用这些事实组织业务故事；程序校验结构、id 和引用。
3. 建模阶段依据业务说明、事实、故事和用户反馈，围绕业务过程形成建模判断，不重新阅读原文或发明业务事实。
4. JSON 编译阶段把建模说明和已校验语义计划转换为结构，不重新设计语义。
5. 业务表达检查阶段使用业务说明和候选模型，验证代表性业务事实是否可表达，必要时局部修正。
6. 映射阶段将事实关联到检查后的最终候选元素，只接受真实存在的元素 id，并明确完整、部分或缺失覆盖。
7. 模型自述和业务过程支撑评估只读取候选模型，不能依赖原文或前序说明替模型补齐缺失语义。

这种边界使每个阶段的责任清楚：业务理解负责说清楚业务，建模负责把业务语义编译为模型，表达检查负责发现真实缺口，过程评估负责判断候选模型自身是否能支撑它声明的过程。

## 交接、核对与恢复

业务理解提交时同时保存原文片段目录和一次独立核对结果。核对从两个方向记录：原文哪些片段没有被说明完整，以及说明中哪些句子缺少原文依据或与原文冲突。核对结果是审阅信息，不会被候选模型的修改掩盖；依据发生变化时，旧核对自动标记为过期。

语义准备先形成带原文依据的事实，再组织引用这些事实的业务故事，并生成少量绑定事实的代表性业务情形。故事和情形是后续建模与检查的交接材料，不能把故事 id 当作事实 id，也不能在映射阶段创造新的业务事实。候选模型生成后，表达检查重新使用这些固定情形；首次检查补充判断，修正后的复查只更新判断，事实、依据和情形由程序冻结。

检查意见按责任分流：模型已经明确而候选无法表达的缺口才进入定点模型修正；说明遗漏或冲突回到业务理解核对；业务本身没有答案的内容进入澄清问题。检查通过表示当前情形可以被表达，不代表原文已经穷尽。修正每轮保存候选、判断和变更记录；如果后续复查使先前通过的情形回归，则恢复到本轮修正前的候选并停止自动循环。

候选、建模说明、业务依据和检查快照都带有版本关联。检查中断时保留最后一个有效候选；可以在版本一致时单独继续“检查当前候选”或“建立事实映射”。映射只读取已检查的候选，版本变化或手工编辑会使映射失效，必须先重新检查。恢复使用保存的业务依据，不把后来追加的澄清问题目录误当成新的业务版本。

## 何时算作缺口

以下情况通常属于真实缺口：

- 无法确定某次业务涉及的是哪一个对象实例；
- 无法区分两种业务结果不同的安排；
- 多方关系无法绑定到同一次业务上下文；
- 只有查询结果，却无法表达实际业务记录或状态变化；
- 操作、规则或过程引用的对象之间存在悬空或矛盾；
- 业务说明明确要求追踪的产出没有可追踪的表达。

以下情况通常不属于缺口：

- 没有细化技术字段、接口、数据库列或算法代码；
- 没有为每个名词建立独立对象；
- 没有把可由关系路径稳定推导出的联系重复建模；
- 没有把另一种尚未被业务要求的设计方案加入模型；
- 业务本身尚未明确，但模型已在边界中诚实保留这种不确定性。

## 质量判断

候选模型的质量不由对象数量、关系数量或提示词章节数量决定，而由它能否用足够简单的元素表达核心业务过程决定。评审时应同时看：

- 业务主体、事项、资源和产出的边界是否清楚；
- 关键联系是否绑定了正确的业务上下文；
- 操作和只读能力是否区分了状态变化与计算；
- 规则是否作用于正确对象并保留关键限制；
- 代表性业务情形能否被模型明确表达；
- 未决边界是否被诚实保留，没有被模型擅自回答。

“检查通过”只表示当前检查用例能够表达，不表示模型已经覆盖原文全部内容。最终仍需要领域专家结合模型自述、业务过程支撑结果和实际业务反馈进行判断。
