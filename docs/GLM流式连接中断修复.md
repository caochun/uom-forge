# GLM 流式连接中断修复

日期：2026-09-28。

## 已确认的问题

BTMS、HBMS 的命令行实验均在建模依据阶段出现 `GLM：terminated`。两次请求已收到 HTTP 200 和思考片段，之后响应体读取失败。命令行直接调用生产建模流程，没有经过浏览器或 `/api/analyze/stream`，因此浏览器断开不是这次复现的原因。

当时配置为 `glm-5.3`、`reasoning_effort=high`，`GLM_API_TIMEOUT_MS=0`、`UOM_PI_TIMEOUT_MS=0`。这些应用层超时没有触发。两次失败接近同一时刻，但没有保留下底层 `Error.cause`，不能据此认定存在固定 240 秒超时，也不能确定是服务端、网关还是网络关闭了连接。

修复后的真实运行再次复现：BTMS、HBMS 的第一条请求分别在约 157159、157163 毫秒收到 `ECONNRESET`，都在已输出思考内容后断开。新逻辑发出 `reset` 并自动开始第二次请求，两边恢复输出。几乎同步的重置提示共享链路因素，但这些证据仍不能确定具体关闭方；也不支持“固定 240 秒应用超时”的判断。

两边恢复后都完成了依据生成。北京时间 14:27:55，BTMS 的独立审阅与 HBMS 的设计请求再次几乎同时重置，并自动恢复；BTMS 已完成的设计仍保留。通过 Node diagnostics channel 和进程 socket 检查，确认这些请求使用直连 IPv6，未经过 shell 中配置的本机 HTTP 代理。系统日志在 14:27:50–51 记录了 IPv6 续租与地址更新，时间上接近，但还不能断定这是重置原因。没有把未经验证的网络归因写成根因结论。

此后 HBMS 独立审阅也在单次请求约 274 秒处收到 `ECONNRESET` 并自动重试。各请求在不同持续时间处被重置，重试后恢复输出；不能用这些现象断言存在固定的应用请求时限。

程序存在两个确定的恢复缺口：

- Pi 适配器仅在尚未收到任何正文、思考或工具片段时重试一次。GLM 先输出思考，随后断开时直接失败。
- 独立审阅、编译、讨论等使用的 Chat Completions 适配器没有流中断重试。

## 本次实现

`server/providers/stream-recovery.ts` 统一识别连接终止、明确的 socket 错误码及缺少结束标记的提前 EOF。每次未完成生成最多重试两次，间隔 500、1000 毫秒；等待可取消，已有阶段总时限继续生效。

Pi 只重新发送当前未完成轮次开始时的消息快照。失败的正文、思考和工具调用不加入历史。Pi 在成功结束一轮之后才执行工具，因此不会执行失败尝试中的工具，也不会重新执行此前已完成轮次的工具。重试不增加设计轮数。SDK 自身的请求重试设为零，避免多层重试放大次数。

两条调用链均发送 `reset` 事件。前端清除当前生成的临时正文、思考及输出片段，保留已完成的业务理解、建模依据、上一轮完整设计和审阅历史。Pi 的重置通知与旧片段共用同一事件队列，保证先消费旧片段，再清理，再接收新片段。

候选模型成功返回并通过结果检查后，编译记录标记为已完成，避免恢复成功后仍显示“模型生成未完成”。

HTTP 鉴权、配额、格式错误、输出长度限制及用户取消不按连接中断重试。重试耗尽后报告可理解的错误及安全错误码，不把截断的输出当作成功结果。

响应体读取错误在被 SDK 简化前保留安全错误码，例如 `UND_ERR_SOCKET`。服务端 `[upstream-stream]` 日志记录 provider、错误码、尝试次数、该次耗时和是否继续重试；不记录密钥、请求正文或 socket 地址。

## 验证

- 150 项自动化测试通过，包含响应头之前的连接重置、思考后中断、正文后中断、提前 EOF、连续失败耗尽次数、取消、等待重试时超时、配额错误和最后完整设计的保留。
- 本地 HTTP 服务发送思考、正文及完整工具参数后强制断开 TCP；实际 Node fetch/SDK 路径检测到 `UND_ERR_SOCKET` 并恢复。工具只执行一次；重试请求保持原始上下文，失败片段未进入历史。
- 浏览器回归通过实际“重新建模”按钮发起请求，向页面注入依据、设计、审阅、编译各阶段的失败片段和重置事件，检查 React 状态及本地草稿，不留下失败片段，保留已完成阶段。
- 类型检查、构建、运行时提示词同步检查通过。构建保留原有的大 chunk 提示。

本次改动处理应用收到上游断流后的恢复与诊断。它不能保证远端服务永不关闭连接；连续三次失败仍会明确结束当前调用。重试是重新生成当前轮次，不是从已收到的 token 继续生成，因此会增加该轮等待时间和调用量。

长时间 GLM/high 验证及 BTMS、HBMS 产物保存在工作区之外的 `domsys/runs/20260928-134505-glm-high-precompile/`；各次失败和人工中断均保留，修复后运行使用 `BTMS-retry-2`、`HBMS-retry-2` 目录，停在 JSON 编译前。

两案最终均完成指定流程，第一轮独立检查给出“可表达”：

| HBMS | 31 分 50 秒 | 3 次：依据、设计、审阅 | 保存 6305 字符的文字设计，编译前结束 |

全部实际请求均核验为 `glm-5.3` / `high`，没有模型 JSON 编译请求。上述耗时包含失败推理与重新生成。建模质量的人工观察另存运行目录中的 `manual-observations.md`；连接恢复成功及模型自审通过不等于业务模型已完全正确。

## 输出额度与连接中断的区别（2026-09-28 补充）

后续设计验收实验的 `GLM 输出未正常完成（length）` 表示达到生成 token 限制，与 `terminated` / `ECONNRESET` 连接中断不同，不能靠相同参数的断流重试解决。

查阅 [官方参数说明](https://docs.bigmodel.cn/cn/guide/start/concept-param#max_tokens) 与 [GLM-5.3 模型文档](https://docs.bigmodel.cn/cn/guide/models/text/glm-5.3)：GLM-5.3 默认 `max_tokens` 为 65536，最大为 131072；提前完成时自然结束。官方接口不提供“无限”值。

历史实验曾将 `.env` 的 `GLM_MAX_OUTPUT_TOKENS` 调整为 131072；该配置只影响当时及之后的请求。

131072 是可用上限，并不保证复杂审阅必然完成，也不修复网络断开。此次独立审阅在 32768 下以 `length` 结束，相同提示词在 65536 下已返回完整报告；生成成功与报告有效性、模型语义正确性仍分别验收。

131072 的对照审阅首轮随后在约 749.7 秒收到 `UND_ERR_BODY_TIMEOUT`：此前约 5 分钟未见新的流式进度，现有恢复逻辑自动重试并恢复输出。应用总时限配置为零不表示底层 HTTP 读取没有超时。这次记录能区分响应体超时与 `length`，仍不能确定上游停止发送内容的原因；未以此为由关闭底层超时。

## DeepSeek 推理模式及 GLM IPv4 对照（2026-09-28）

使用同一 HBMS 冻结设计、局部修补设计的审阅提示词，逐字复用先前 GLM 提示词并核对 SHA-256。DeepSeek 使用官方 `deepseek-flash`、`thinking.type=enabled`、`reasoning_effort=high`；实验进程把输出上限设为 131072，不修改应用的 DeepSeek 配置。每份提示词各运行两次，通过现有生产 Provider 和流恢复代码调用。

| 对照 | 完整返回次数 | 耗时 | 异常断流 / 重试 |
| --- | --- | --- | --- |
| DeepSeek 冻结设计 | 2/2 | 150.237、175.089 秒 | 0 / 0 |
| DeepSeek 局部修补设计 | 2/2 | 246.978、132.787 秒 | 0 / 0 |
| GLM 局部修补设计，IPv4 | 1/1 | 752.090 秒 | 0 / 0 |

DeepSeek 实际连接均为 IPv4；公开基址探测显示 GLM 默认连接选择 IPv6。为减少路径干扰，另用 `--dns-result-order=ipv4first` 运行一条 GLM/high/131072 同提示词对照，实际 socket 确认 IPv4，亦无中断。此前 GLM 早期运行有 IPv6 记录，但最近一次响应体超时的具体连接没有地址族日志，不能把探测结果冒充该次失败连接的直接证据。

本次没有复现 DeepSeek 的 `terminated`，但当时仍不能确认 GLM 后端服务或 IPv6 是根因。可能性仍包括 GLM Coding 网关/生成服务的间歇性停顿，以及到该服务的网络路径；供应商、时刻、生成速度与持续时间尚不构成严格单变量对照，因此当时没有据此修改产品的网络选址配置。随后在取消输出上限后的同请求 IPv4/IPv6 对照中获得了地址族差异证据，见下文，代码现已默认选择 IPv4。

“完整返回”只表示生成响应传输完成；这五份报告仍有引文、覆盖或 JSON 结构校验问题，未计作传输错误。底层诊断还记录了正常结束时 `reader.cancel()` 引起的 `AbortError`（code 20），与 `completed` 时刻一致，属于本地清理，不算上游异常断流。原始事件均保留。

## 取消应用输出上限（2026-09-29）

DeepSeek、Qwen 和 GLM Provider 均不再读取或发送 `LLM_MAX_OUTPUT_TOKENS`、`QWEN_MAX_OUTPUT_TOKENS` 或 `GLM_MAX_OUTPUT_TOKENS`。`.env` 中的 GLM 配置项已删除；旧环境变量即使存在也会被忽略。Pi Agent 的模型 `maxTokens` 仅作为 pi-ai 必需的元数据和思考预算参考；流调用内部传入 `0` 作为省略哨兵，OpenAI adapter 因此不会生成上游 HTTP 的 `max_tokens` 字段。

请求使用服务商自己的默认输出策略，并仍受服务商模型上限、上下文窗口、响应体超时和费用规则约束。“不发送 max_tokens”不等于无限生成，也不会取消上游的 `length` 或网络中断。

## IPv6 路径对照与默认选择（2026-09-29）

取消输出上限后的两案运行中，BTMS 与 HBMS 均曾在 GLM 已输出大量思考内容后收到 `ECONNRESET`。对同一份完整设计检查请求逐字重放，仅改变 DNS 地址族顺序：`ipv6first` 实际使用 IPv6 socket，约 190 秒后收到 `read ECONNRESET`；`ipv4first` 实际使用 IPv4 socket，在相同时间仍持续输出。请求哈希、模型 `glm-5.3`、`high` 强度及未发送 `max_tokens` 均相同。

因此 GLM Provider 默认设置 `dns.setDefaultResultOrder('ipv4first')`，通过 `GLM_DNS_RESULT_ORDER` 可选择 `ipv4first`、`ipv6first` 或 `verbatim`。这只改变新连接的地址选择；如果 IPv4 路径本身或 GLM 服务端仍关闭连接，原有的响应体清理与最多两次重试继续生效，不能保证远端永不断流。
