# 业务理解与候选建模的语义交接

第一阶段解释业务，第二阶段决定如何表达为模型。规范与业务领域无关，不包含样例业务的预设对象或规则。第一阶段输出 Markdown，不生成模型字段表，也不生成额外的结构化阅读提纲。

## 第一阶段的 11 项判断

| 要回答的问题 | 对应章节 |
| --- | --- |
| 业务主体是谁？ | 业务主体与业务事项 |
| 主体提出或处理什么事项？ | 业务主体与业务事项 |
| 哪些东西具有独立身份，可以长期管理和重复引用？ | 可持续管理的资源和业务产出 |
| 哪些只是属性、状态、指标、阈值或计算结果？ | 业务输入、判断规则与计算依据、临时计算结果 |
| 哪些业务产出需要记录或追踪？ | 可持续管理的资源和业务产出 |
| 对象间有哪些明确的业务联系？ | 业务事实与对象联系 |
| 哪些联系来自临时计算？ | 临时计算结果 |
| 哪些行为会创建记录或改变状态？ | 业务过程与状态变化 |
| 哪些行为只是查询、计算、校核或评估？ | 业务过程与状态变化 |
| 哪些分支属于同一概念的类型差异？ | 业务主体与业务事项 |
| 哪些为材料明确、上下文推断或尚未说明？ | 对应段落标明，不确定事项汇总 |

固定章节为：业务概述、业务输入、业务主体与业务事项、可持续管理的资源和业务产出、业务事实与对象联系、业务过程与状态变化、判断规则与计算依据、临时计算结果、不确定事项。无材料依据时写“材料未说明”，不能为了补齐标题而编造内容。章节检查只能发现缺项，不能代替语义审查。

需要用户作答时另附“待确认问题”，编号列出。有限选项在下一行以“选项：…”或“多选：…”提供，使用分号分隔；其他问题使用文字回答。原始说明保留，答案独立保存并成为后续反馈。

## 第二阶段 A：建模判断

输入只有业务说明，迭代时增加当前候选模型的业务字段和用户反馈。旧模型里的引文、来源字段、界面状态不进入提示词。没有业务说明时不能启动建模。

输出 Markdown 建模说明，明确对象边界、关系方向和上下文、业务操作的目标与效果、只读能力及其输出、规则、业务过程和待确认事项。概念存在不依赖业务过程已开展。临时结果不默认独立建模；如说明明确要求保存和独立追踪，也不能仅凭“结果”一词禁止成为对象。本轮不细化属性。

## 第二阶段 B：模型整理

新的一次模型调用只接收 A 的说明和紧凑的输出结构要求，不继承 A 的会话历史，不重新阅读业务说明或原文。完整 Schema 只用于程序校验，不展开到提示词。不改变 A 中作出的建模决定，将它们整理为 object、relation、action、function、rule 和 activity。

本地校验 JSON 结构、全局 id、关系端点、目标及规则和活动引用。错误直接反馈，不静默删掉引用或补造对象。所有原文 evidence 为空；原文由系统保存，证据关联目前留待审阅或后续功能。

A 的说明在 B 启动前发布给前端。B 失败或被停止，不抹掉 A 的说明，也不覆盖已有图模型。格式正确不代表与 A 完全语义等价，仍需结合模型自述和后续支撑评估审阅。

前端可以单独重试 B，传入已保存的完整说明。若用户已经改动业务理解、问题答案或建模反馈，说明对应的版本已过期，应重新建模，不能把旧说明的整理结果视为最新模型。

两次调用可能增加总开销，需要分别记录首个输出和完成耗时再评价性能；不能仅凭超时把原因归结为提示词长或推理复杂。
