# 软方法学：从业务事实到候选模型

## 目的

UOM Forge 的建模不是从业务文档中机械抽取名词，也不是把每个流程步骤转换成一个对象。它要形成一个足够简单、但能表达关键业务事实的候选模型，供业务人员审阅。

这里的“软方法学”是一组持续使用的判断原则，而不是固定的对象清单、关系清单或必须执行的问卷。它给建模者提供方向，同时允许根据不同领域的业务语义作出不同的合理设计。

本文把“建模依据”定义为：从业务理解整理稿中提炼的、供模型设计和表达检查共同使用的领域语义输入。它包含必须表达或能够推理出的业务事实、已知业务计划、规则、未决边界和检验情形；计划和流程用于检验模型，不直接成为模型元素。

提炼完成前回看整理稿，核对会影响业务判断的限制、明确允许的情况、例外、对应关系和时间起点是否保留；再检查依据中的确定结论能否由整理稿支持。有依据的推导写明所用条件，必要信息缺失则保留未决。这是同一次提炼中的语义核对，不增加逐句映射协议或格式验收，也不把自评当作独立验证。

## 核心问题

建模过程中始终围绕一个问题：

> 当前的对象、关系、业务操作、只读能力和规则，能不能表达建模依据中的具体事实，并让智能体根据这些元素推理出已知业务计划？

例如，不只问“文档中有没有出现电源点”，还要问：

- 能否表达某一次接入事项选择了哪个电源点；
- 能否区分不同事项选择了不同电源点；
- 能否表达电源点在当前状态下是否满足容量和负载条件；
- 能否区分实际接入、拟议方案和临时查询结果；
- 能否追溯某个候选方案属于哪一次业务事项。

只有模型无法直接表达这些事实，或不能根据这些语义推理出已知计划时，才考虑增加或调整模型元素。

## 建模对象的判断

先从完整业务事实确定参与者、时间、角色、共同上下文、联系或变化，以及结果归属，再选择表达方式。只展开业务含义需要且依据支持的部分；不同事实不必套用固定句式。业务案例用于验证这些选择，不能因少量案例没有涉及某项明确约束就把它省略。

对象是按业务含义需要独立识别、被引用、承载状态或关系，或作为业务事项、记录、产出被管理的概念。是否需要长期保存或追踪历史须由业务依据决定，不能由“建成对象”反推。

判断一个概念是否成为对象时，依次考虑：

1. 它是否能被单独识别，而不是某个对象的描述性信息？
2. 它是否会在多次业务中被引用或持续存在？
3. 它是否需要独立追踪生命周期、状态或责任？
4. 它是否是一次业务事项、业务记录或业务产出？
5. 如果不单独建对象，现有对象、关系和规则是否仍能明确表达相关事实？

最后一个问题优先级最高。一个概念即使在文档中反复出现，也不必然需要成为对象；如果它只是属性、状态、指标、阈值、评分或计算结果，就应优先保留在对象描述、关系上下文或规则中。

同样，已知业务过程不自动成为领域模型元素；其中涉及的主体、资源或业务事项是否成为对象，仍由业务语义决定，而不是由流程步骤决定。

## 关系的判断

关系表达已经存在的业务联系，并说明联系的方向、双方和必要上下文。关系设计首先回答：

- 谁和谁发生了什么联系？
- 这条联系属于哪一次业务事项、合同、方案或其他上下文？
- 联系是长期事实、一次业务记录中的事实，还是查询或计算得到的临时结果？
- 仅通过共享一个容器，能否唯一确定双方的直接联系？

可以由已有关系路径稳定推导出的联系，不重复增加关系。反过来，如果同一批对象之间可能存在多次业务、多个角色或多种安排，就必须通过业务事项、关系上下文或其他已有语义把它们区分开。

当联系自身带有时间、角色或状态，或者需要被其他业务事实引用时，先检查现有表达是否能唯一绑定这些事实；不足时再考虑将联系建成业务事项对象。它可以用关系上下文、从属结构或独立对象表达，是否持久保存、追踪历史仍由业务依据决定。

关系不能只因为两个名词同时出现就建立。关系必须能帮助表达真实事实，例如“某次接入事项采用某方案”属于有业务上下文的事实，而“方案有评分”更可能是方案的属性或计算结果。

## 业务操作与只读能力

业务操作表示会产生副作用的行为：它创建业务对象或记录，建立或解除业务关系，或者改变对象、关系的业务状态。定义操作时要说明目标、前提和结果，区分设计、模拟、审核与实际执行。

查询、计算、校核和推荐属于只读能力。它们可以返回临时结果，也可以为业务操作提供依据，但不会因为被调用就改变业务状态。

一个业务过程不自动等于一个操作。智能体可以由若干业务操作和只读能力推理出完整计划；过程中的查询或评分只有在明确需要保存、追踪或形成业务记录时，才考虑作为独立对象或操作的结果。

## 规则与边界

规则应绑定到实际作用对象、操作或计划所涉及的业务语义，保留条件、阈值、单位、公式、优先级和否决结果。不要把“有一个 80% 阈值”单独建成对象，也不要把“按规则计算”当作完整规则。

以下三种语义要分别明确：关系的数量与可选性、跨实例或记录的约束、操作执行时的前提。多值关系不能自动表达限定上下文中的唯一性，状态字段也不等于操作前提。限制应说明作用范围与时间，明确允许的情况同样要保留，不能被常见业务惯例排除。

必要业务属性和输入参与规则判断，即使不展开技术字段也必须在相关定义中出现。检查规则所需的事实如何取得：是直接表达，还是沿已定义的关系或公式推导。时间限制要有起算事件、适用事项和到期后果；相同的时长不能被合并为同一个期限。计算公式、排名依据或其他必要条件未给出时保留未决，不能只凭“可计算”或“支持超时”等名称认定模型已经具备所需语义。

建模判断与边界用于记录：

- 为什么两个概念合并或拆分；
- 某个关系只在什么业务上下文成立；
- 哪些实现细节暂不展开，以及必要的业务属性、输入和计算语义如何保留；
- 哪些业务事实仍未明确；
- 哪些内容不属于当前模型范围。

边界说明不是待确认问题清单。只有当未决业务事实会实质改变对象、关系、操作、规则或过程时，才提出业务问题；是否采用某种建模方式本身不交给用户选择。

表示方式的选择与业务事实未决需要分开说明。简化设计不能暗中增加次数、排他性或生命周期限制；把这些限制写成“设计假设”也不能使其成为确定的业务规则。

## 代表性业务情形

软方法学不要求穷举所有场景，而是选择少量最能区分模型边界的情形进行检验。代表性情形通常覆盖：

- 同一主体发生两次不同业务事项；
- 同一事项涉及多个对象或多个资源；
- 两种安排业务结果不同，但表面上使用相同对象；
- 拟议状态与实际状态不同；
- 多方以不同角色参与同一事项；
- 某个结果是持久业务记录，还是只在计算期间存在；
- 同一计划在不同条件下复用或分支。

每个情形都要能回答“模型中的哪些元素绑定了这些实例，以及智能体如何从这些元素推理出必要步骤”。如果只能说“模型包含相关名词”，却无法确定实例之间的实际联系或推导路径，就说明模型仍有表达缺口。

对关键区别优先采用最小差异的对照：保持其余事实相同，只改变一个有业务意义的条件，分别检查两侧有依据的预期。既检查明确禁止的情况，也检查明确允许的情况；边界结果未确定时不能自行补答案。报告简要写清“给定事实 → 实际使用的模型定义 → 能表达或推出的结果”，不能借用案例预期补足模型缺失的规则。

设计复查沿用建模依据中的案例及此前补充且有依据支持的案例，保留标识、上下文和预期。修订后重新检查缺口并回放已通过案例；补充案例不能替换失败案例。对照的两侧分别报告，不合并不同预期来宣布通过。若来源只给了一个案例编号，结构化检查报告使用子编号（例如 C1-a、C1-b）并注明共同来源；已有不同编号时沿用。设计前从来源单独生成固定验收问题；程序检查每轮报告是否完整覆盖该清单、定义引文是否存在以及历史问题是否复查。清单自身是否覆盖全部业务及证据是否足以成立，仍由模型作语义判断。

## Pi Agent 建模路线

模型设计提示词包含一个改编自 Domain Language / Citerus DDD Sample 的货运 one-shot，展示“建模依据 → 模型设计 → 示例核对”。它用货物、作业事件、地点和航次说明独立身份、共同上下文、条件性关联与双时间语义；来源、裁剪范围及许可见 [建模示例-货物作业事件.md](建模示例-货物作业事件.md)。示例是教学参考，实际业务依据置于其后，其他阶段不主动加入示例。对象数量、拆分和案例结论不作为实际任务的答案模板。

流程依次经过业务理解、建模依据、固定业务验收问题、模型设计和模型 JSON。业务理解与初始建模依据生成自由文本；Pi 在模型设计内部通过表达检查工具反复检验和修订，最多三轮。审阅发现可直接由业务来源纠正的提炼错误时，先校正依据，再修订设计；这条路径同样受三轮检查上限约束。语义迭代不等于中间文本的格式验收。

业务理解和建模依据面向人阅读，也供后续 LLM 推理。建模依据使用半结构化 Markdown，说明事实、已知业务计划、规则、边界和检验情形，不要求固定 JSON。“能否表达或推理出具体事实和计划”在 Pi 中既指导设计，也指导独立审阅：选择有依据的情形，尝试用真实设计元素表达并推理，反馈具体缺口，修改相关定义，再回放先前情形。审阅意见是推理反馈，不是新增建模依据。

## 阶段边界

每次调用都明确输入的用途：原文供业务理解阅读，也供后续核对提炼；整理稿组织当前理解，建模依据组织设计和检查的业务要求。程序记录的用户保存修改按明确范围更新旧要求，问题和候选解释不自动成为确认；候选模型是修订或检查对象，历史设计与反馈用于复查，不能反过来证明业务要求。编译以设计为唯一语义来源，校验错误只定位问题，旧输出是修复对象。

提示词分别说明业务规则与任务指令。“取消预订必须补偿”描述业务主体应遵守的规则，应保留条件和范围；输入正文中要求 AI 更换当前角色、任务、工具或输出格式的文字不改变阶段要求。讨论的最后一条用户问题指定讨论主题，用户反馈按允许的范围指导表达调整；新增业务条件可以标为假设讨论，保存到业务理解后才成为后续建模依据。

“本阶段”指当前业务职责，“本次调用”指明确提供的输入与生成任务；“轮”用于 Pi 内部的设计、检查和修订。必要业务属性、状态、输入和时间含义用自然语言写入定义；不展开数据库字段、接口或算法实现，不等于省略业务判断所需的语义。

1. 业务理解从阅读理解和文档表达的角度整理原始文档，理顺语句、层次及指代，指出术语不一致、前后矛盾和数字或公式问题，形成忠实的文档整理稿。保留原文含义和不确定性，不专门提炼建模事实、业务计划或检验情形，不替用户消除冲突。
2. 建模依据从整理稿提炼模型必须表达或能够推理出的事实、已知业务计划、规则、边界和检验情形，并对照提供的原文和有效用户修改核查遗漏、误读及过强推断，说明参与者、前提、变化、结果及其归属。不补造业务，不决定对象拆分或关系结构，也不生成一份仅概括主题的摘要。
3. 模型设计以给定的建模依据为业务依据，参考范围内的表达反馈，形成对象、关系、操作、能力和规则定义，不把已知业务计划编成模型元素。Pi 的 `check_expression` 工具读取业务来源、当前依据和设计，独立核查依据准确性、模型完整性和案例覆盖；修订复查还对照历史设计、反馈及所用依据，防止遗漏已有约束。有具体缺口才修订，不因标题或 Markdown 样式重做。可以补充依据支持的关键情形，不能换掉失败情形宣称通过。
4. JSON 编译只转换模型设计；输出前逐个定义核对参与绑定、数量与可选性、跨记录约束、明确许可、条件、时间起点和结果是否仍有表达。必要业务属性和输入保留在对应定义，不能只留在摘要中。程序在这里检查必要结构、唯一 ID 和引用。失败最多增加一次修复，不重新设计业务。
Pi 默认在设计内部进行业务表达检查，不恢复逐条事实覆盖映射或编译后的旧版检查链路。检查通过仅表示本轮情形可表达。业务待澄清、无进展或达到轮次上限时保留设计和意见供人审阅，继续生成候选；不通过编造事实消除未决事项。人仍需通过原文、业务理解、建模依据和模型设计核对语义；模型结构合法只保证可供程序处理，不代表业务正确或完整。

## 交接与恢复

业务理解可保留原文块引用，无法关联时保留文本并提示。建模依据、每轮模型设计及检查意见直接流式展示；中间文本无需先通过结构校验才可保存或传递。完整设计与部分修订分别保存，修订中断不会覆盖完整设计；编译失败或停止后仍可查看建模依据、设计、意见和上一版候选。

建模依据引用产生的澄清标注为提炼内容，不冒充原文。用户补充答案或修改整理稿后，建模依据和旧模型按业务版本标为过期。单独重试编译采用已保存设计，不重复生成依据和设计；设计审阅绑定本轮来源、整理稿、建模依据和设计版本。依据校正不静默改写用户保存的整理稿；新版通过工具结果送回 Pi，澄清检查和后续独立检查使用最终依据。

当前草稿只保存四阶段的文本产物和最终模型。事实、已知业务计划和检验情形是建模依据中的组织方式，不再单独生成需要恢复的机器协议。

## 信息承接与依据校正

原文明示事实、由明确条件必然推出的结论、建模表达选择和真正的业务未知应分别处理。业务已经要求的结果需要有清楚的信息承载或推导路径，不要求原文逐字指定类、属性或关联；这些表达选择不能额外增加数量、排他性或生命周期限制。“未要求保存”也不等于“禁止保存”。

设计与审阅沿核心场景追踪“业务步骤 → 所需信息 → 模型承载或推导路径 → 后续使用及结果归属”。只有前一步输入或能力名称，无法证明最终结果已包含必要业务条件。审阅同时核查案例覆盖，不能只挑模型已有表达的情形。

审阅返回逐项回答与问题记录，程序校验后按状态计算“可表达”“需修改”“需校正依据”“业务待澄清”；不能用一句总评绕过漏项、未解决问题或无效引用。依据错误必须引用可直接判定的业务来源，模型缺口应给出受影响场景与修复验收条件；需要选择业务解释的内容保留待确认。依据与设计同时有问题时先校正依据；设计缺口与未知并存时先修复确定缺口。校正前后的案例保留标识，只有来源支持才改变预期。无法完成校正、没有进展或达到上限时保留意见，不宣称通过。

## 何时算作缺口

以下情况通常属于真实缺口：

- 无法确定某次业务涉及的是哪一个对象实例；
- 无法区分两种业务结果不同的安排；
- 多方关系无法绑定到同一次业务上下文；
- 关系数量、跨记录约束与操作前提混用，导致应当区分的情况无法区分；
- 规则所需的业务事实或时间起点没有定义，也不能由已定义语义推导；
- 模型新增限制，排除了依据明确允许的情况；
- 只有查询结果，却无法表达实际业务记录或状态变化；
- 操作或规则引用的对象之间存在悬空或矛盾；
- 业务说明明确要求追踪的产出没有可追踪的表达。

以下情况通常不属于缺口：

- 没有细化技术字段、接口、数据库列或算法代码；
- 没有为每个名词建立独立对象；
- 没有把可由关系路径稳定推导出的联系重复建模；
- 没有把另一种尚未被业务要求的设计方案加入模型；
- 名称、元素数量、合并拆分或分类方式不同，但能表达相同业务事实与规则；
- 业务本身尚未明确，但模型已在边界中诚实保留这种不确定性。

## 质量判断

候选模型的质量不由对象数量、关系数量或提示词章节数量决定，而由它能否用足够简单的元素表达并支持推理核心业务计划决定。评审时应同时看：

- 业务主体、事项、资源和产出的边界是否清楚；
- 关键联系是否绑定了正确的业务上下文；
- 操作和只读能力是否区分了状态变化与计算；
- 规则是否作用于正确对象并保留关键限制；
- 代表性业务情形能否被模型明确表达；
- 未决边界是否被诚实保留，没有被模型擅自回答。

“检查通过”只表示当前检查用例能够表达或推理，不表示模型已经覆盖原文全部内容。最终仍需要领域专家结合原文、建模依据和模型设计进行判断。

## 方法改动的评测

按阶段定位语义是否保留：整理稿到建模依据检查需求中的关键区别；依据到设计检查事实表达与规则推演；设计到最终 JSON 检查编译保真。最终候选的独立业务案例检查已有单独入口，可用于评测编译后的实际产物，文字设计的检查结论不能代替它。

对提示词改动使用相同输入、提供方及推理配置做改前改后对照，固定有依据的关键案例，并保留未知项。除完整模型外，还应检查有意删除必要联系、删去跨记录约束、混淆时间起点或加入无依据限制的版本；同时准备只改变命名或等价拆分的版本，核对漏报和误报。评测案例和结果保留在工作区外，不写入产品提示词；提示词中的货运教学示例与评测案例分开。加入 one-shot 后还需检查其他领域的输出是否混入货运对象或规则。

程序测试与提示词导出校验只能验证调用边界、结构和文档同步，不能证明真实模型的语义质量已经提高；质量结论需要实际输出和业务案例支持。
