# Pi Agent 高压接入文档耗时调试报告

## 结论

使用 `高压接入方案业务规则说明1.docx` 做了真实运行。当前 `.env` 使用 `glm-5.3-flash`、Coding Plan endpoint、`GLM_REASONING_EFFORT=max`、`GLM_MAX_OUTPUT_TOKENS=32768`，Pi 阶段默认总时限为 300 秒。

这次耗时由三部分叠加：GLM 开启思考后的单次推理本身较慢；Pi Agent 为工具交接、独立核对和失败后的再次生成增加了请求；每个回合都携带完整历史和完整业务说明，导致请求上下文持续变大。文档只有约 3,578 个正文字符，因此“文档太大”不是主要原因。

当前最直接的失败表现是：Pi 业务理解阶段在总时限内没有完成 `finish_understanding`，最后抛出“Pi 业务理解超时（超过 300 秒）”。之前页面显示“任务未完成”或“覆盖检查未完成”，属于同一条链路的结果：核对调用未及时返回或返回内容未通过 JSON 校验，Agent 又进入了下一轮，直到总时限被耗尽。

本报告前半部分记录的是改造前的真实运行。随后已按报告建议改造业务理解路径：模型先直接生成草稿，检查器只返回 `gaps`，宿主持有草稿并在必要时发起一次定向修正，不再使用 `finish_understanding` 工具交接。改造后的实现和测试结果见文末。

## 调试输入和方法

- 输入文件：`高压接入方案业务规则说明1.docx`。
- 使用 Mammoth 读取 DOCX；本轮诊断脚本另按标题和段落提取 115 个块，并非前端实际的顶层 DOM 分块。
- 共得到 115 个正文块，正文文本约 3,578 个字符。块中包含章节标题、编号标题和规则段落。
- 真实运行覆盖了 Pi 业务理解路径；另外用同一文档、同一模型和 `low` 思考级别运行了直接调用路径作为对照。
- 对 Pi 直接使用的 `streamSimple` 请求增加了临时 HTTP 观测；调试脚本没有提交到仓库。

为了避免把 `max` 的一次超时误认为偶然网络故障，另做了 `GLM_REASONING_EFFORT=low` 的对照。`low` 只用于定位调用结构，不能代表当前 `.env` 的生产耗时。

## 真实运行数据

### 当前 max 配置

在当前配置下，Pi 业务理解真实运行超过 300 秒，阶段超时，没有完成业务理解工具交接。Pi 请求走 `server/providers/pi.ts` 的 `streamSimple`，没有经过普通 `runProviderTurn` 的 timing 事件，所以原有运行记录不能直接告诉前端每一个 Pi HTTP 请求花了多久。

### Pi 路径的 low 对照

下面是同一文档在 `low` 下的实际 HTTP 记录。前四次请求完成，第五次请求在阶段总时限到达时被中止。

| 请求 | 用途 | 请求体 | 首包 | 总耗时 | 响应字节数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | Pi 初次生成并调用 `check_understanding` | 10.6 KB | 5.1 s | 81.6 s | 950,792 |
| 2 | 独立业务理解核对 | 13.7 KB | 1.4 s | 59.6 s | 707,503 |
| 3 | Pi 根据核对结果再次生成并再次调用检查 | 18.4 KB | 3.7 s | 55.2 s | 948,933 |
| 4 | 第二次独立业务理解核对 | 13.7 KB | 0.7 s | 69.6 s | 795,774 |
| 5 | Pi 试图继续交接最终结果 | 26.5 KB | 3.7 s | 33.9 s 后被总时限中止 | 未完成 |

前四次完整请求已经消耗约 265 秒。第五次不是新的业务阶段，而是为了完成工具交接产生的额外模型回合。

第 2、4 次核对的输入都包含完整业务说明和 115 个原文块，输入 prompt 约 12,357 个字符；核对协议要求对每个原文块返回 `complete`、`partial` 或 `uncovered`，并且还要检查新增和冲突。这使输出非常长，也使 JSON 输出更容易在模型响应过长、被中止或夹带解释时无法解析。

这次 low 运行中，第一次核对被程序判定为“业务理解核对不是有效的 JSON”，Agent 因此又生成了一轮业务说明并重新检查。该现象增加了请求次数；报告只记录已观测到的错误，不把具体截断位置推断为唯一原因。

### 直接调用基线

同一文档、同一 GLM 模型和 `low` 配置下，关闭 Pi、直接执行业务理解：

| 路径 | HTTP 请求数 | 总耗时 | 结果 |
| --- | ---: | ---: | --- |
| 直接调用 | 2 | 176.0 s | 返回业务理解；核对结果保留了一个待复核警告 |
| Pi Agent | 至少 5 | 超过 300 s | 未完成 `finish_understanding` |

直接调用的两次请求分别是业务说明生成和一次独立核对；Pi 在这两个基本请求之外增加了两次工具驱动的生成回合和一次未完成的最终交接回合。

网络连接不是主要瓶颈。Pi low 记录中各请求连接建立时间约为 0.7–5.1 秒，首包也在几秒内到达；大部分时间消耗在模型持续输出思考内容和工具参数。单次响应达到约 0.7–0.95 MB，也印证了思考输出和工具参数的规模较大。

## 已确认的代码原因

### 1. 当前配置让每个 Pi 回合都使用 max 思考

`server/providers/glm.ts` 的 `glmGenerationOptions` 读取 `GLM_REASONING_EFFORT`，并始终发送 `thinking: { type: 'enabled' }`。当前 `.env` 是 `max` 和 32,768 个输出 token。Pi Agent 创建时虽然写了 `thinkingLevel: 'minimal'`，但 `server/providers/pi.ts` 又把 GLM 的 `reasoning` 和 `samplingParams` 覆盖为环境配置，因此 `minimal` 不能降低 GLM 的思考级别。

### 2. 业务理解天然包含多个串行模型回合

`server/agents/pi-understanding.ts` 的正常路径至少包含：初次生成、独立检查、根据检查修正、第二次独立检查、最终工具交接。独立检查在 `check_understanding` 工具内部再次调用 `reviewUnderstanding`，所以一次工具调用实际上包含另一个完整的 GLM 请求。

代码允许最多 8 个 Agent turn；独立检查虽然限制为两次，但第二次检查后只是把“请立即提交”返回给模型，仍需要额外模型回合调用 `finish_understanding`。当前 low 记录正是在第 5 个请求交接时被总时限中止。

### 3. 独立核对强制逐块返回 115 项结果

`server/stages/understanding-review.ts` 要求对每个输入 block 原样返回一个 coverage 项，程序随后逐块检查结果。前端导入的标题、编号标题和规则段落都成为 block；本例 115 个 block 中有不少只提供章节上下文，仍然进入逐块核对。

这会同时扩大输入和输出。更严重的是，核对结果是一个很长的 JSON；一旦模型输出不完整或混入额外文本，`parseJsonOutput` 就会把整轮核对判为未完成，Pi 又会开始下一轮。

### 4. Pi 对话历史重复携带完整业务说明和完整 narrative

初次请求包含系统提示、完整原文块和工具定义；工具参数又携带完整业务理解 Markdown。下一轮请求会把上一轮的 assistant tool call 和 tool result 一起发回模型。实测请求体从 10.6 KB 增长到 18.4 KB，再增长到 26.5 KB。

独立核对还单独接收完整业务说明和完整 115 个原文块。因此同一份内容在 Pi 历史、工具参数和独立核对请求中重复传输。

### 5. Pi 请求没有接入普通 provider 的 timing 观测

直接调用使用 `createChatCompletionsProvider`，会产生连接、首段输出和完成时间的 timing 事件。Pi 使用 `createPiStream` 直接调用 `streamSimple`，当前只转发 delta 和阶段事件，没有同等的请求级 timing。结果是前端只能看到“正在理解/正在核对”，不能看到当前第几个模型请求、已经等待多久、是否已经收到首包。

## 对先前页面错误的解释

- “Pi Agent 未通过提交工具交接业务理解”：模型还在生成、核对调用被中止，或总时限在 `finish_understanding` 回合完成前到达；不等价于业务文档一定无法理解。
- “覆盖检查未完成”：独立核对请求没有在总时限内返回可解析且完整的 JSON，或者返回内容缺少某些 block 的有效 coverage。
- “发现几十项未覆盖”：当前协议按原文 block 报告差异，标题、编号和片段级拆分会放大计数；它不是模型元素数量，也不应直接作为再次完整重写 narrative 的唯一依据。
- “原输出已保留、等待审阅”：这是超出两次检查上限后代码允许的降级路径。它避免无限循环，但在总时限较短时仍可能来不及走到该路径。

## 建议的修复优先级

1. **先把 Pi 的思考级别和输出预算按阶段拆开。** 业务理解、覆盖核对、事实提取和 JSON 校验使用 `low` 或受控的 `high`；只在确实需要复杂推理的候选模型阶段使用更高级别。为结构化核对设置较小的输出上限，并在达到上限时返回可识别的截断状态。
2. **把覆盖核对改成“只返回缺口”。** 程序可以把没有返回的 block 视为未核对，但模型只输出确有遗漏、冲突或无依据新增的 block id；不要要求模型重复返回 115 个 complete 项。对标题和纯编号块可在核对前合并为上下文或排除，原始 block 引用仍由程序保留。
3. **第二次核对后由宿主直接提交最后一次已检查的 narrative。** 在 `independentAttempts >= 2` 且 narrative 具备必需章节时，不再额外消耗一个 GLM 回合让模型重复把全文放入 `finish_understanding` 参数；将待复核差异作为结果状态持久化。
4. **减少工具参数中的全文复制。** 让 Agent 工具提交 draft id、版本号或增量修订，全文由宿主内存和持久化草稿保存；独立核对也只接收必要的事实块和摘要。这样既降低上下文，也避免工具调用参数本身成为最大输出。
5. **给 Pi 请求补齐 timing 和请求编号 SSE 事件。** 至少显示阶段、回合、请求开始时间、首包时间、累计耗时和中止原因。用户可以区分模型仍在推理、独立核对耗时，还是工具交接失败。
6. **保留核对原始响应和解析错误摘要。** 当前解析失败后只留下“不是有效 JSON”，无法判断是截断、代码围栏、额外说明还是字段缺失。保存脱敏后的原始响应元数据，才能继续针对 GLM 的输出协议修复。

这些修改应先在高压文档上验证：业务理解应能在一个初始生成、至多一次缺口核对和一次宿主提交内结束；如果仍有待复核项，也应保存草稿并允许用户继续，而不是等待第二个完整 narrative 回合。

## 改造后验证

使用同一份高压接入 DOCX、此前诊断脚本的分块方式和 `GLM_REASONING_EFFORT=low` 做真实运行，改造后的 Pi 业务理解完成了“生成草稿 → 缺口检查 → 一次定向修正”流程，总耗时约 213 秒。没有出现 `finish_understanding` 工具交接，也没有要求检查器返回每个 block 的 complete 记录；缺口检查仍保留原文 block id，原文依据和用户复核状态继续持久化。

代码验证结果：144 项测试通过，TypeScript 类型检查、生产构建和 UI 检查通过。当前实现将完整 narrative 只作为 Agent 的草稿消息保留，检查结果和修正请求使用缺口摘要；检查器输出格式为 `{"gaps": [...]}`，没有问题时返回空数组。

## 结论边界

本报告确认了请求数量、上下文重复、阶段总时限、逐块核对协议以及 GLM 思考配置造成的耗时和失败路径。单次 GLM 响应中具体有多少 token 用于思考、哪一段导致某次 JSON 解析失败，需要保留完整响应或使用 provider 级 token usage 才能进一步定量；本报告没有把这部分推测写成确定结论。


## 后续提示词与调用精简（2026-09-20）

本次改动在上述业务理解简化的基础上，进一步缩减理解章节与建模提示词，移除后续输入中重复的事实 source 引文，编译仅接收建模说明。Pi 建模直接输出 Markdown，不再强制 finish 交接，也不在编译前重复启动独立检查；编译后的实际候选仍接受统一表达检查。业务理解修正改为程序原子应用段落替换，不再生成完整修订稿。

新一轮实验通过浏览器执行实际 `documentToBlocks`，得到 57 个顶层块、3,578 个正文字符。表格作为一个顶层块保留，旧实验的 115 块不能声称与前端分块相同。实验重新冻结本次改动前后的代码，并统一模型、推理级别和输入开展比较；旧报告的 213 秒只能作为历史记录。详见 [提示词与调用精简验证](Pi%20Agent提示词与调用精简验证.md)。
