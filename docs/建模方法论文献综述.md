# 建模方法论文献综述：从经典概念建模到 LLM 驱动领域建模

本文档为 [软方法学：从业务事实到候选模型](./软方法学：从业务事实到候选模型.md) 提供文献定位：UOM Forge 的建模方法在已有研究中的亲缘脉络、共性做法与差异点。检索与整理时间为 2026 年 9 月；链接以写作时可访问为准。

组织为四条线：面向对象分析与领域建模的经典方法（第 1 节）、本体论指导的概念建模与事实导向建模（第 2、3 节）、概念模型质量理论（第 4 节）、LLM 驱动建模的最新工作（第 5 节），最后给出与本项目方法论的对照（第 6 节）。

## 1. 面向对象分析与领域建模的经典脉络

### 1.1 ER 模型：概念建模的起点

Chen（1976）提出实体-关系模型，用实体、属性、联系表达业务数据结构，奠定了"用概念结构表达业务事实"的范式。此后几乎所有概念建模语言——包括本项目的 `CandidateModel`（objects/relations/…）——都在它的坐标系内：概念、联系、约束三分。

### 1.2 "方法战"与 UML：notation 统一，method 从未统一

1980 年代末到 1990 年代初出现了大量竞争性的面向对象分析方法（所谓 method wars）：

- **OMT**（Rumbaugh 等，1991）：对象模型、动态模型、功能模型三视图；
- **Booch 方法**（Booch，1994）：从类与对象的结构循环演进设计；
- **OOSE/Objectory**（Jacobson，1992）：用例驱动，从业务过程出发界定系统边界。

1994 年 Rumbaugh 加入 Rational 与 Booch 合流，1996 年 Jacobson 加入（"三友"），1997 年 OMG 采纳 **UML** 作为标准表示法。这段历史对本项目最重要的教训是：**业界统一的是表示法（notation），而"怎么建模"的方法论（method）从来没有被 UML 统一**——每个方法背后对"什么该成为对象、关系表达什么"的判断原则各不相同。UOM Forge 的软方法学本质上是在 notation 确定之后，重新把 method 显式化、可执行化。

### 1.3 职责驱动设计（RDD）：对象因职责而存在

Wirfs-Brock 等（1990）提出职责驱动设计与 CRC（Class-Responsibility-Collaboration）卡：从对象**承担的行为职责**出发做设计，职责写"做什么"而非"怎么做"；对象因职责与协作而存在，而不是因为持有数据（Wirfs-Brock & McKean《Object Design》2004 发展了角色、职责、协作三要素）。本项目区分"业务操作（有副作用）"与"只读能力（查询/计算/校核/评估）"是职责思路的直接体现，且比经典 RDD 走得更远——把只读能力升为一等建模元素，贴合方案设计、模拟、校核类业务（如高压接入方案）的语义。

### 1.4 领域驱动设计（DDD）

Evans（2003）是当前实践影响最大的领域建模体系：

- **Entity（由身份定义）vs Value Object（由属性定义、无身份）**——对应本项目对象判断里"能否单独识别、是否需要独立身份"；
- **Aggregate**（一致性边界 + 聚合根）——对应"结果归属、参与绑定必须清楚"；
- **Bounded Context / Ubiquitous Language**（模型适用边界、业务与开发共享语言）——对应本项目"建模依据是人机共读的中间产物"与模型边界的显式记录。

差异：本项目不引入聚合与仓储等实现层概念，候选模型停留在业务语义层；并且对象判断的最后一问"不单独建对象还能否表达事实"具有**高于一切的反向检验优先级**，比 DDD 的分类判据更偏最小主义。

### 1.5 需求工程侧的关联

三条经典线与"业务理解/建模依据"的阶段分工相关：

- **KAOS**（Dardenne、van Lamsweerde & Fickas，1993）：目标-精化-障碍分析，把需求组织成目标树与领域性质（domain properties）的网；本项目"建模依据保留领域性质、规则不退化为'按文档规定'"与之相通。
- **i\***（Yu，1997）：参与者、目标、软目标的早期需求建模，强调多方角色依赖。
- **Problem Frames**（Jackson，2001）：明确区分**领域事实（domain）与需求（requirement）**，要求把需求投影到领域事实上去满足——本项目"整理稿/建模依据（事实）→ 模型设计（表达方案）"的分野与之一致，检验情形则类似 Jackson 的"规格要可投影到领域描述"。

## 2. 本体论指导的概念建模：把"什么该是对象"变成可判定问题

### 2.1 TOVE 与能力问题（Competency Questions）——与本项目最同构的经典工作

Grüninger & Fox 在 TOVE（Toronto Virtual Enterprise）项目中提出（1995）：构建本体（企业模型）之前先写下它**必须能回答的问题**（competency questions），用这些问题界定范围、指导设计，并在建成后作为**表达能力是否充分**的评价标准；问题的形式化还用于推导本体所需的表达构件。综述见 Monfardini 等（2020）。近年 CQ 已成为本体工程的需求规范与评估标准做法，并被引入 LLM 评估流程（Lippolis 等，2025，见 5.2 节）。

本项目的"核心问题 + 检验情形"与 CQ 方法同构：先定义待表达的事实，再验证模型能否表达。差异在于本项目把检验下探到**实例级可区分性**（"A用X/B用Y"与"A用Y/B用X"必须可区分；E1 与 E2 的结果必须可分开追溯），比经典 CQ 的查询级检验更尖锐，也更容易暴露"模型里有这个名词"式的假通过。

### 2.2 Bunge-Wand-Weber（BWW）：信息系统的形式本体

Wand & Weber 以 Bunge 的系统哲学为基础建立信息系统表征模型（1990 起的系列工作）：事物、性质、状态、状态变换、事件、法则，并以此**评价建模语言的本体充分性**——语言的构件若无法刻画本体概念则为不完整，多个构件映射同一本体概念则为冗余（经典应用如用 BWW 分析 UML；Rosemann 2002 形式化了 BWW 元模型）。本项目强调区分实际发生/拟议安排/临时计算结果、操作改变状态而只读能力不改变，都是 BWW 式的本体关切。

### 2.3 OntoClean：类资格的元属性判据

Guarino & Welty（2000/2002）提出用**身份（identity）、刚性（rigidity）、依赖（dependence）、统一性（unity）**等元属性审查本体分类结构：例如一个概念若对某些实例是本质的、对另一些是偶发的（anti-rigid），就不该作为这些实例的父类。这套判据回答"一个概念**是否有资格**成为独立类"，是"对象判断五问"在形式本体侧的亲缘。本项目未显式使用 OntoClean 词汇，但"属性、状态、指标、临时结果不自动成为对象"与"身份判据先行"的精神一致。

### 2.4 UFO 与 OntoUML：生成式的本体驱动建模

Guizzardi（2005 博士论文起）发展的 UFO（Unified Foundational Ontology）区分类型（type）与实例（instance）、内在性质与外在性质（moments）、关系的具体发生（relator）等，并由 UFO 直接**生成**建模语言 OntoUML——语言构件与本体范畴一一对应（综述见 Guizzardi 等的 UFO story 与 ontouml.org）。UFO 对"同一类型的两次具体发生必须可区分""relator 本身可以是一等个体"的分析，恰好覆盖本项目高压接入场景里"方案（拟议实例）、接入事项（实际发生）、计算结果（临时）"的区分。这是与本项目模型结构最可直接对接的形式化工具，若未来需要更强的语义约束（如自动一致性检查），OntoUML/UFO 是最自然的升级路径。

### 2.5 本体工程方法学：生命周期与阶段划分

本体工程侧的三大经典方法学：**METHONTOLOGY**（Fernández-López 等，1997，借鉴软件工程的开发-维护生命周期）、**On-To-Knowledge**（Sure 等，2003，面向知识管理应用的可行性-启动-精化-评估流程）、**NeOn**（Suárez-Figueroa 等，2012，场景化、支持本体复用的九种构建情形）；比较综述见 Corcho、Fernández-López & Gómez-Pérez（2003，被引逾千次）。它们共同的结构是"规格说明 → 概念化 → 实现 → 评估"，其中**规格（要回答什么/要表达什么）先行**与本项目"建模依据先于模型设计"一致；差异是这些方法学以本体工程师为中心，不处理"业务文档不可信、有歧义"的输入现实——这正是本项目"业务理解阶段只整理不裁决"所要解决的问题。

## 3. 事实导向建模：ORM/NIAM

Halpin 等发展的 ORM（Object-Role Modeling，源自 NIAM）把一切建模为**自然语言事实**（对象扮演角色的 n 元事实读法）加约束：

- **Verbalization**：全部事实与规则都能翻成业务人员可读的自然语言句子，供非技术业务方逐条确认；
- **Population check / 具体实例检验**：设计过程中用具体实例填充检验模型能否区分、约束是否成立（CSDP 流程报告此步骤显著提高正确率）；
- 业务规则（约束、推导规则）是一等公民，而非附属文档。

本项目的"建模依据=事实/故事/规则的自然语言 Markdown，人机共读 + 检验情形回放"与 ORM 哲学同源：**模型要能翻回业务语言，并用具体事实验证**。差异是本项目不要求事实表、二元角色或固定 schema（事实/故事用自由文本组织），以换取对长文档和 LLM 中间产物的适应性；代价是无法像 ORM 那样对事实做形式化的约束推导。

## 4. 概念模型质量理论：什么叫"好模型"

- **SEQUAL 语义质量框架**（Lindland、Sindre & Sølvberg，1994；Krogstie 等扩展）：从符号学层次定义模型质量——语法质量（符合语言语法）、语义质量（与领域的对应：完整 + 有效）、语用质量（受众正确理解），后续扩展至物理、社会维度。**语法质量可程序判定，语义与语用质量必须回到领域与受众**——这正是本项目"结构校验通过 ≠ 业务正确、编译只管结构、语义交回人审"的理论依据。
- **Moody & Shanks（1994）"What makes a good data model?"**：基于专家建模的实证研究给出质量属性集——完整性、**最小性（不表达超出需求的内容）**、可理解性、健壮性、灵活性等，并指出**完整性与最小性存在张力**，好的模型是权衡而非单目标最大化。本项目"最小充分模型、质量不由元素数量决定、能不建就不建"是该张力的明确立场。
- **Nelson、Monarchi & Burton** 的综合框架合并了 SEQUAL 与 Moody-Shanks 两派。

## 5. LLM 驱动的领域建模与本体工程（2023–2026）

### 5.1 域模型抽取与自动建模

- **Chen、Yang、Chen、Hernández López、Mussbacher、Varró（MODELS 2023）"Automated Domain Modeling with Large Language Models: A Comparative Study"**（本仓库根目录有全文 PDF）：系统比较 LLM 从文本生成域模型（UML 类图）的提示技术（zero-shot、few-shot、CoT 等），结论是单轮抽取质量有限、对复杂模式（如关联类）尤差。这是本项目"不靠单轮抽取、靠阶段拆分与迭代"的直接反例依据。
- **Yang、Mussbacher、Varró（2024）"Multi-step Iterative Automated Domain Modeling with Large Language Models"**：把建模拆成多步提示词链、逐步注入指令与人类知识、迭代修正，显著优于单轮——与本项目"理解 → 依据 → 设计 → 检查"的阶段拆分思路同向。差异：其目标是与 ground truth 类图的结构相似度，本项目目标是业务表达可审阅；其人类知识注入靠人工脚本，本项目靠人审中间产物与澄清回传。
- **Arulmohan（2023，McMaster 硕士论文）**：从敏捷 backlog 文本抽取域模型与 state-of-practice 工具对比；**Prokop（2024）**：LLM 概念建模实验。两者同样以结构相似度评价。

### 5.2 LLM 本体工程与评测

- **Mateiu & Groza（2023，arXiv:2307.16699）**较早系统实验 LLM 用于本体工程任务；**Li 等的系统文献综述（Semantic Web Journal）**梳理了 LLM 在本体工程各活动中的角色与输入输出配置。
- **LLMs4OL 共享任务（2024/2025）**把本体学习变成社区评测基准；**Aggarwal 等（2026）**报告 LLM 在学术本体生成上可达高 F1——但基准多为术语/层次结构匹配。
- **Nejah 等（HAL）对 LLM 本体学习评测实践的批评**：现有评测几乎都以与 ground truth 的（结构/语义）相似度为指标，缺少对**模型是否真的表达了目标业务**的功能性评测。
- **Lippolis 等（2025，arXiv:2507.14552）"Large Language Models Assisting Ontology Evaluation"**：用 LLM 辅助基于 CQ 的本体评估——把 2.1 节的经典 CQ 方法和 LLM 结合，方向与本项目一致，但其 CQ 由人维护、评价对象是已有本体，不是"生成-检验一体、证据可追溯"的闭环。

### 5.3 迭代自评机制

**Self-Refine**（Madaan 等，NeurIPS 2023，arXiv:2303.17651）：同一 LLM 生成-反馈-精化的通用范式；**Reflexion**（Shinn 等，2023）：带语言化反思记忆的迭代。本项目 `check_expression` 设计-检查循环是该机制在建模任务上的实例化，特点是：(a) 检查者作为**独立调用**（同一份建模依据、无会话历史），避免自评偏置被上下文放大；(b) 检查反馈**不得升格为业务事实**；(c) 无进展/超限时**诚实保留**而非无限迭代。

### 5.4 实践侧：Event Storming 与现代 DDD

Brandolini 的 Event Storming（工作坊形式，以领域事件为锚点协作梳理业务过程）与 DDD 社区近年实践，代表"从行为/过程切入领域建模"的工程流派。它与本项目的"业务故事"阶段目标一致（围绕同一事项的过程性组织），但依赖现场协作，不解决"从遗留文档单方面建模"的问题。

## 6. 与 UOM Forge 软方法学的对照

| 本项目做法 | 最近亲缘 | 差异/特色 |
| --- | --- | --- |
| 核心问题 + 检验情形驱动建模与检查 | TOVE 能力问题（Grüninger & Fox 1995） | 检验下探到实例可区分性，比查询级 CQ 更严格 |
| 建模依据 = 事实/故事/规则的自然语言 | ORM 事实导向、verbalization | 自由 Markdown、无事实表/固定 schema；人机共读 |
| 对象判断五问，"能不建就不建"优先 | DDD Entity/VO + OntoClean 身份判据 + Moody 最小性 | 三线判据合并为单一优先级序列 |
| 业务操作 vs 只读能力 | RDD 职责驱动 | 只读能力为一等元素，贴合设计/校核类业务 |
| 实例/模板、实际/拟议/临时结果的区分 | BWW 状态与事件、UFO type/instance/relator | 未用形式本体词汇，靠判断原则实现同构关切 |
| 设计-检查循环（≤3 轮，独立检查者） | Self-Refine / Reflexion / Yang 2024 多步迭代 | 反馈不得当新事实；失败诚实保留；证据链追溯 |
| 未决边界诚实保留，不替用户裁决 | Moody 完整性-最小性张力；KAOS 障碍分析 | "不冒充原文、不假设答案"落实为流程约束而非事后说明 |
| 结构校验 ≠ 业务正确 | SEQUAL 语法/语义质量分层 | 程序只管可处理性，语义判断交还人 |

**定位主张**：现有 LLM 建模工作（含 Chen/Yang 系列）的评价目标几乎都是"与 ground truth 模型的结构相似度"，Nejah 等的评测批评也确认了这一点。"以表达能力验证（CQ 的实例化）为目标、以事实导向依据为人机交接面、以证据链追溯和未决保留为约束"的自动建模方法，在文献中尚属空白。若需要学术化，可主张的贡献点是：把 CQ 检验从"查询能否回答"细化为"业务上不同的情形能否区分"，并以独立的表达检查智能体实现生成-检验闭环。

**局限**：本综述为定向检索而非系统综述；经典文献以代表作覆盖，未逐一穷举；5.1/5.2 节对论文结论的转述以摘要与检索结果为准，引用前建议核读原文。
