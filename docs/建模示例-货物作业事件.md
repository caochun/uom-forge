# 建模 one-shot：货物作业事件

模型设计阶段使用一个“建模依据 → 模型设计 → 示例核对”的教学示例，示范如何保留独立身份、绑定一次业务的参与对象、表达条件性关联，以及区分具有不同业务含义的时间。

示例文字位于 [modeling-example.ts](../server/stages/modeling-example.ts)，由 `modelDesignPrompt` 拼入设计提示词。完整运行时文本见 [运行时提示词-领域建模流程.md](运行时提示词-领域建模流程.md) 的“03 模型设计”。修改示例后运行 `npm run docs:prompts`，避免维护两份不同的示例正文。

## 裁剪与设计选择

本例范围是作业事件登记与相关事实表达。原系统的路线规划、配送状态推导、聚合边界、消息处理、仓储和 ORM 实现均未纳入示例输入。原项目的事件等价判断和重复上报处理也不纳入本例要求。不能从这份裁剪后的教学示例推断原系统缺少这些能力。

输出选择货物、作业事件、地点、航次四类对象，三条以事件为共同上下文的关系，一个登记操作及两项规则。这个数量不是其他领域的模板。原项目的 Domain Event 在当前模型类型中以业务记录对象表达，事件类型和两个时间保留为自然语言定义的业务属性。示例没有为凑齐元素类型额外增加只读能力。

“航次零或一个”概括整个事件集合上的数量，类型规则进一步限定具体事件允许的值；登记操作显式引用同一约束作为前提。已知引用、输入完整及类型约束满足，只表示满足本例的登记要求，不表示已经核对航线、先后顺序或所有实际运输条件。

## 运行时边界

示例仅拼入模型设计阶段，使用 `<modeling-example>` 包围，并在前后说明用途。实际业务输入置于示例后，标为“实际任务的建模依据”。模型应学习表达方式与判断方法，不复制货运事实、对象、规则、实例或核对结论。

业务理解、建模依据提炼、独立设计审阅、JSON 编译、独立案例检查、模型自述和讨论的提示词均不主动拼入示例。设计审阅仍只根据实际建模依据检查实际设计；编译仍只处理生成的设计。如果设计模型错误地复制了教学内容，后续调用仍可能收到被污染的设计，因此提示词分隔并不等于程序能够保证语义隔离。

示例核对是对教学设计的解释，不属于模型设计正文，也不替代 Pi 的 `check_expression`。实际设计仍按原流程提交完整设计并调用检查工具。

## 验证边界

程序测试与文档导出校验用于检查运行流程及文档同步。one-shot 是否改善建模质量，仍需固定实际输入、模型与推理配置，对比加入示例前后的输出。重点检查条件性关联和时间含义是否保留、是否新增无依据限制，以及非货运案例中是否出现示例内容。保留原有 CSV 案例作为评测输入，不将其参考答案加入教学示例。
