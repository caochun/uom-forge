# Pi 建模验收问题与定义证据

本次修改解决检查报告用整体概述代替逐项核查的问题。设计前从业务来源生成固定验收清单，每轮检查必须回答清单中的所有问题并引用当前定义；程序核对覆盖、引用及历史问题，再决定是否需要修订。

## 领域无关的实现

运行时代码只处理问题、来源、验收预期、定义证据和问题状态。验收内容由本次原文与保存的整理稿生成；代码与通用提示词没有内置具体案例的对象、属性、关联或业务规则。外部回归样例不进入产品提示词。

业务理解、建模依据和设计仍使用 Markdown。新增结构化产物用于检查完整性，不要求将设计提前编译成模型 JSON，也不检查类名或字段名是否符合某个参考答案。

## 实际调用与修订

1. 业务依据生成后，`designAcceptancePrompt` 独立生成验收清单。该调用不接收建模依据、当前候选模型、表达调整反馈或教学示例，避免从现有设计反推检查范围。
2. 先形成注明假设的代表性场景与目标达成时的具体业务事实，再从结果反推验收问题。清单保存场景、结果、问题编号、来源原句、必要性、依据性质和预期；聚焦核心结果的信息承接，其余条款和案例仍由完整审阅核查。无需套用固定领域字段。
3. Pi 设计接收这份清单。`check_expression` 使用同一清单、当前依据、业务来源、当前设计及历史报告逐项检查。
4. 审阅按问题返回当前定义原句、引用的作用、假设场景、实际可表达的结果及缺口。间接路径需逐段检查到真正承载信息的定义；关联存在不能替代被关联对象的内容定义。
5. 程序验证报告后生成可读反馈，完整传回 Pi。正常调用通过工具结果回传，未调用工具时通过 follow-up 回传。修订完整设计后，所有验收项和历史问题重新检查。

清单在一次建模循环中保持不变，依据校正也不会重新生成或删除清单。若验收预期本身有误，审阅必须保留原问题，以 `not-applicable` 明示来源依据及原因；依据有提炼错误则走原有依据校正分支。审阅中的问题不能自动成为新增业务要求。

## 程序能校验什么

- 清单非空、编号唯一、来源引文存在于本次提供的原文或整理稿。
- 每轮报告恰好回答所有清单问题，不重复、不漏项、不使用未知编号。
- 定义引文存在于当前设计；修复证据存在于当前设计或当前依据。旧设计中的文字不能当作新版证据。定义引用可兼容 Markdown 强调、行内代码标记及中英文引号样式差异；使用 Markdown 解析器识别标记，不删除字词、否定、数字或字面运算符，不做模糊或语义匹配。业务来源引文仍只归一化空白。
- “有定义支持”必须有引用且没有未解决缺口；“已保留未决边界”必须引用相关定义并说明边界。
- 历史问题（包括已解决问题）不得消失、改号或改弱问题及验收条件；宣布解决必须有当前修复证据。模型问题的解决引用设计，依据问题的解决引用依据。
- 未解决依据错误优先触发校正；模型缺口触发修订；阻断性业务未知请求澄清。只有有实际支持项、无待修问题且报告校验通过时，才得到“可表达”。全部声称不适用或仅有未决边界不能证明模型通过。

引用只检查原句是否存在，不把它当作语义正确性的证明。清单是否覆盖业务、引用是否足以支撑结论、推导是否过强以及未决边界是否真实，仍由 LLM 判断。

## 保存、失败与开销

`DesignReview` 保存清单及版本，各轮保存结构化报告、所用依据与清单版本。界面展示“本次业务验收问题”和可读检查报告，刷新后保留。结构化 JSON 正文不直接流入用户界面；未通过校验的原始报告可展开查看。

清单结构完整但引文抄写不匹配时，最多调用一次引文定位；只接受原编号和对应原句，程序只替换 sourceQuote，问题、预期、场景和结果均保持不变。无法找到原句、编号不完整或试图修改其他字段时仍报失败。清单生成失败时停止设计，保留建模依据；清单生成中取消同样保留已完成产物。报告无效时保留完整设计、原始报告和校验原因，不宣称通过、不自动改写模型。检查失败、待澄清或达到上限后仍沿用已有的候选编译行为，编译成功不意味着设计审阅通过。

首轮通过时，从业务理解到模型编译共六次调用，比原流程增加一次清单生成。Pi 仍最多三轮设计检查；依据校正不重置轮次。清单引文校正按需增加一次调用；没有为检查报告格式问题增加自动修复调用。

## 验证方式

自动回归验证清单与候选隔离、完整性校验、来源和定义引用、历史问题复查、依据校正、工具与 follow-up 反馈、取消、失败保存及浏览器展示。它们不证明模型语义质量。

可使用通用脚本对外部设计进行独立复审：

```bash
npx tsx scripts/review-designs.ts --input /absolute/path/fixture.json --provider glm --effort high
```

使用 `--acceptance /absolute/path/saved-acceptance.json` 可复用设计前已生成的清单；仍校验来源引文，且仅按上述规则修复抄写差异。

输入包含 `narrative`、可选 `sources`、`businessBasis` 和 `designs: [{ name, text }]`。脚本先生成一次清单，各设计使用相同清单独立审阅，互不接收对方的审阅意见。输出目录保存输入、提示词、原始报告、程序验收结果及实际调用计时。脚本不生成或编译模型。

完整拼接提示词由实际函数导出至 [运行时提示词-领域建模流程.md](运行时提示词-领域建模流程.md)，共 18 段。

## 本次验证记录（2026-09-28）

173 项自动测试、类型检查和构建通过。自动测试包含 Pi 工具回传与未调用工具时的 follow-up 修订、固定清单与历史问题复查，也包含 Markdown 引用兼容及拒绝删改否定、数值、运算符的回归用例。浏览器检查验证保存和展示；这些程序测试不证明语义审阅质量。

真实 GLM/high 复审使用工作区外的业务来源、冻结旧设计和人工局部修补对照；不向模型提供 CSV 的参考 Classes/Associations 或人工缺口诊断。人工对照只修补结果内容及承接，不是完整金标准。本次真实调用是独立审阅对照，尚不能据此声称 Pi 已在真实调用中完成多轮修订。

32768 输出额度下，完整审阅多次以 `length` 结束，没有报告正文。相同输入和提示词改为 65536 后，冻结旧设计的审阅在约 682 秒返回完整报告，识别出结果内容承接及供给可用性两类模型缺口。原报告省略 Markdown 标记并转换引号，最初被严格匹配拒收；兼容纯格式差异后，对同一原始报告重新校验，得到“需修改”。没有修改报告文字或重新向模型提供缺口答案。

此前实验曾将 `.env` 的 `GLM_MAX_OUTPUT_TOKENS` 设为 131072；具体参数依据及与连接中断的区别见 [GLM 流式连接中断修复](GLM流式连接中断修复.md)。2026-09-29 起，Provider 已取消应用主动发送的 `max_tokens`，由服务商默认策略决定输出额度。

局部修补对照使用 131072，首轮响应体超时后自动重试，合计约 1478 秒返回完整报告。原始报告将搜索条件对应、最终选择承接两项从缺口改判为有定义支持，仍指出未修补的供给可用性缺口。但 Q8/Q12 的定义引文把“向旅客收取”写成了“向该旅客收取”，属于内容增字，程序拒收并记为 unknown；没有扩大格式兼容范围让它通过。

这次观察支持审阅方向有所改善，但不能证明 GLM 能稳定满足引文契约，也不能证明真实 Pi 多轮修订已成功。两份报告的输出额度不同，本次只作定性观察。完整记录、未经修改的报告、拒收原因和计时见工作区外的 [运行记录](/Users/chun/Downloads/uom-forge-evaluation/domsys/runs/20260928-171600-glm-high-control-review-128k/运行记录.md)。
