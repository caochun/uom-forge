# 软方法学：从业务事实到候选模型

## 目的

UOM Forge 的建模不是从业务文档中机械抽取名词，也不是把每个流程步骤转换成一个对象。它要形成一个足够简单、但能表达关键业务事实的候选模型，供业务人员审阅和后续过程支撑评估。

这里的“软方法学”是一组持续使用的判断原则，而不是固定的对象清单、关系清单或必须执行的问卷。它给建模者提供方向，同时允许根据不同领域的业务语义作出不同的合理设计。

## 核心问题

建模过程中始终围绕一个问题：

> 当前的对象、关系、业务操作、只读能力和规则，能不能表达一个具体的业务事实或业务过程？

例如，不只问“文档中有没有出现电源点”，还要问：

- 能否表达某一次接入事项选择了哪个电源点；
- 能否区分不同事项选择了不同电源点；
- 能否表达电源点在当前状态下是否满足容量和负载条件；
- 能否区分实际接入、拟议方案和临时查询结果；
- 能否追溯某个候选方案属于哪一次业务事项。

只有现有模型无法表达这些事实时，才考虑增加或调整模型元素。

## 建模对象的判断

对象是具有独立业务身份、需要被长期管理、能够被重复引用，或者本身是需要追踪的业务事项、记录或产出的概念。

判断一个概念是否成为对象时，依次考虑：

1. 它是否能被单独识别，而不是某个对象的描述性信息？
2. 它是否会在多次业务中被引用或持续存在？
3. 它是否需要独立追踪生命周期、状态或责任？
4. 它是否是一次业务事项、业务记录或业务产出？
5. 如果不单独建对象，现有对象、关系和规则是否仍能明确表达相关事实？

最后一个问题优先级最高。一个概念即使在文档中反复出现，也不必然需要成为对象；如果它只是属性、状态、指标、阈值、评分或计算结果，就应优先保留在对象描述、关系上下文或规则中。

同样，业务过程尚未发生，不代表其中涉及的主体、资源或业务事项没有独立身份。对象的成立依据是业务语义，而不是某个操作是否已经执行。

## 关系的判断

关系表达已经存在的业务联系，并说明联系的方向、双方和必要上下文。关系设计首先回答：

- 谁和谁发生了什么联系？
- 这条联系属于哪一次业务事项、合同、方案或其他上下文？
- 联系是长期事实、一次业务记录中的事实，还是查询或计算得到的临时结果？
- 仅通过共享一个容器，能否唯一确定双方的直接联系？

可以由已有关系路径稳定推导出的联系，不重复增加关系。反过来，如果同一批对象之间可能存在多次业务、多个角色或多种安排，就必须通过业务事项、关系上下文或其他已有语义把它们区分开。

关系不能只因为两个名词同时出现就建立。关系必须能帮助表达真实事实，例如“某次接入事项采用某方案”属于有业务上下文的事实，而“方案有评分”更可能是方案的属性或计算结果。

## 业务操作与只读能力

业务操作表示会产生副作用的行为：它创建业务对象或记录，建立或解除业务关系，或者改变对象、关系的业务状态。定义操作时要说明目标、前提和结果，区分设计、模拟、审核与实际执行。

查询、计算、校核、评估和推荐属于只读能力。它们可以返回临时结果，也可以为业务操作提供依据，但不会因为被调用就改变业务状态。

一个业务过程不自动等于一个操作。完整过程通常由若干业务操作和只读能力共同支撑；过程中的查询或评分只有在明确需要保存、追踪或形成业务记录时，才考虑作为独立对象或操作的结果。

## 规则与边界

规则应绑定到实际作用对象、操作或业务过程，保留条件、阈值、单位、公式、优先级和否决结果。不要把“有一个 80% 阈值”单独建成对象，也不要把“按规则计算”当作完整规则。

建模判断与边界用于记录：

- 为什么两个概念合并或拆分；
- 某个关系只在什么业务上下文成立；
- 哪些属性和算法本轮有意不细化；
- 哪些业务事实仍未明确；
- 哪些内容不属于当前模型范围。

边界说明不是待确认问题清单。只有当未决业务事实会实质改变对象、关系、操作、规则或过程时，才提出业务问题；是否采用某种建模方式本身不交给用户选择。

## 代表性业务情形

软方法学不要求穷举所有场景，而是选择少量最能区分模型边界的情形进行检验。代表性情形通常覆盖：

- 同一主体发生两次不同业务事项；
- 同一事项涉及多个对象或多个资源；
- 两种安排业务结果不同，但表面上使用相同对象；
- 拟议状态与实际状态不同；
- 多方以不同角色参与同一事项；
- 某个结果是持久业务记录，还是只在计算期间存在；
- 同一过程在不同条件下复用或分支。

每个情形都要能回答“模型中的哪些元素绑定了这些实例”。如果只能说“模型包含相关名词”，却无法确定实例之间的实际联系，就说明模型仍有表达缺口。

## 两条建模路线

direct 和 Pi 使用相同阶段：业务理解、业务依据、模型设计、模型 JSON。两者输入边界、方法和最终模型校验相同。业务理解与业务依据各生成一次自由文本；direct 一次生成设计，Pi 在模型设计内部通过表达检查工具反复检验和修订，最多三轮。语义迭代不等于中间文本的格式验收。

业务理解和业务依据面向人阅读，也供后续 LLM 推理。它们可以采用不同标题和分组，不要求先转成固定字段的事实或故事 JSON。“能否表达具体事实或过程”在 Pi 中既指导设计，也指导独立审阅：选择有依据的情形，尝试用真实设计元素表达，反馈具体缺口，修改相关定义，再回放先前情形。审阅意见是推理反馈，不是新增业务依据。

## 阶段边界

1. 业务理解从阅读理解和文档表达的角度整理原始文档，理顺语句、层次及指代，指出术语不一致、前后矛盾和数字或公式问题，形成忠实的文档整理稿。保留原文含义和不确定性，不专门提炼建模事实、故事或情形，不替用户消除冲突。
2. 业务依据从整理稿提炼模型需要表达的事实与过程，说明参与者、前提、变化、结果及其归属，组织故事，完整保留明确规则和未决边界，选择具体检验情形。不补造业务，不决定对象拆分或关系结构，也不生成一份仅概括主题的摘要。
3. 模型设计直接依据本轮业务依据和设计反馈，沿用其检验情形形成对象、关系、操作、能力、规则与过程定义，不再同时传入完整整理稿。输出可读文本，不强制章节格式。Pi 的 `check_expression` 工具读取同一份业务依据和当前正文，独立检查其表达能力；修订复查还对照上一版设计和历史反馈，防止遗漏已有约束。有具体缺口才修订，不因标题或 Markdown 样式重做。可以补充依据支持的关键情形，不能换掉失败情形宣称通过。
4. JSON 编译只转换模型设计；程序在这里检查必要结构、唯一 ID 和引用。失败最多增加一次修复，不重新设计业务。
5. 模型自述和过程支撑评估是用户单独启动的审阅，只读取候选模型。

Pi 默认在设计内部进行业务表达检查，不恢复逐条事实覆盖映射或编译后的旧版检查链路。检查通过仅表示本轮情形可表达。业务待澄清、无进展或达到轮次上限时保留设计和意见供人审阅，继续生成候选；不通过编造事实消除未决事项。人仍需通过原文、业务说明和模型设计核对语义；模型结构合法只保证可供程序处理，不代表业务正确或完整。

## 交接与恢复

业务理解可保留原文块引用，无法关联时保留文本并提示。业务依据、每轮模型设计及检查意见直接流式展示；中间文本无需先通过结构校验才可保存或传递。完整设计与部分修订分别保存，修订中断不会覆盖完整设计；编译失败或停止后仍可查看业务依据、设计、意见和上一版候选。

业务依据引用产生的澄清标注为提炼内容，不冒充原文。用户补充答案或修改整理稿后，业务依据、旧模型及检验结果按业务版本标为过期。单独重试编译采用已保存设计，不重复生成依据和设计；设计审阅绑定本轮整理稿、业务依据和设计版本。

历史草稿的结构化事实、故事、情形及检查快照继续可读。历史 verify/map 恢复保留版本与引用校验，但不会进入新建模的默认链路。事实和故事是组织业务知识的方法，并不要求每一个中间结果都拥有机器协议。

## 何时算作缺口

以下情况通常属于真实缺口：

- 无法确定某次业务涉及的是哪一个对象实例；
- 无法区分两种业务结果不同的安排；
- 多方关系无法绑定到同一次业务上下文；
- 只有查询结果，却无法表达实际业务记录或状态变化；
- 操作、规则或过程引用的对象之间存在悬空或矛盾；
- 业务说明明确要求追踪的产出没有可追踪的表达。

以下情况通常不属于缺口：

- 没有细化技术字段、接口、数据库列或算法代码；
- 没有为每个名词建立独立对象；
- 没有把可由关系路径稳定推导出的联系重复建模；
- 没有把另一种尚未被业务要求的设计方案加入模型；
- 业务本身尚未明确，但模型已在边界中诚实保留这种不确定性。

## 质量判断

候选模型的质量不由对象数量、关系数量或提示词章节数量决定，而由它能否用足够简单的元素表达核心业务过程决定。评审时应同时看：

- 业务主体、事项、资源和产出的边界是否清楚；
- 关键联系是否绑定了正确的业务上下文；
- 操作和只读能力是否区分了状态变化与计算；
- 规则是否作用于正确对象并保留关键限制；
- 代表性业务情形能否被模型明确表达；
- 未决边界是否被诚实保留，没有被模型擅自回答。

“检查通过”只表示当前检查用例能够表达，不表示模型已经覆盖原文全部内容。最终仍需要领域专家结合模型自述、业务过程支撑结果和实际业务反馈进行判断。
