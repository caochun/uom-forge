# Pi 建模来源校核与修订

后续的固定验收清单、逐项定义证据及报告校验机制见 [Pi建模验收问题与定义证据.md](Pi建模验收问题与定义证据.md)。本文下方保留上一轮修改及当时复测结果。

本次修改针对 BTMS、HBMS 文字建模中发现的两个问题：提炼后的依据错误可能被设计和审阅共同接受；模型虽然列出操作和规则分支，却没有完整承载最终业务结果所需的信息。

## 输入与建模要求

建模依据、Pi 设计和独立审阅同时接收当前整理稿、原文快照及来源关联。新业务理解保留全部原文块，包括整理稿没有引用的块，并记录完整性。旧草稿没有完整性标记时只声明部分核查；没有原文则只核对整理稿。程序记录的用户保存修改按明确适用范围更新对应旧要求，问题与候选解释不自动成为确认。

提示词区分原文明示事实、明确条件的必然推导、建模表达选择和真正的业务未知。表达已有业务需要的属性、从属结构与关系由建模者决定，不能因原文没有使用建模术语就不表达；这些选择也不能增加未经支持的排他性、数量、时序或生命周期规则。

对推导使用反例检验：如果存在符合业务来源但结论不成立的情况，它只是候选解释。推导或未决标签不能替代证据，也不能让该解释在操作效果或案例预期中无条件成立。整理稿写“未建立联系”同样不是免除必要业务表达的依据。

核心场景检查先从业务来源确定结果所需的信息，再用少量假设实例值从输入追踪到结果，逐步说明业务步骤、所需信息、模型承载位置或推导路径，以及后续使用与归属。信息只出现在搜索输入中、操作有名字却没有必要前提或效果，都不足以证明业务已表达。审阅同时检查案例覆盖，允许语义等价的不同对象划分和间接关系路径。

## 循环行为

| 审阅结论 | 程序行为 |
| --- | --- |
| 可表达 | 结束设计循环，保留验证范围和边界 |
| 需修改 | Pi 修订完整设计，再审阅 |
| 需校正依据 | 根据同一业务来源生成完整新版依据，通过工具结果交回 Pi，再修订设计并复查 |
| 业务待澄清 | 保留候选及未决问题，不自行选择业务答案 |

依据错误必须能够由实际提供的业务来源直接判定；审阅反馈本身不是业务事实。依据校正不改写用户保存的整理稿。依据错误和模型缺口同时存在时先校正依据；明确模型缺口与业务未知并存时先修复确定缺口。

整个循环仍最多三轮检查，依据校正不重置轮次。校正结果与旧依据相同时停止，检查/校正失败或取消时保留完整产物。每轮保存依据正文和版本，当前审阅绑定来源、整理稿、依据和设计；依据变化后复查受影响案例并回放其余案例。历史案例保持标识，预期只有业务来源支持时才能改变。新版依据用于最终产物、澄清检查和后续独立案例检查。

前端接收校正状态和完整新版依据；校正中的临时片段或连接重试不会覆盖已有完整依据。各轮审阅可展开对应设计和依据。单独重试编译仍只转换设计；来源、依据或设计版本改变后，不复用旧的通过结论。

## 验证

158 项自动测试、TypeScript 类型检查、生产构建和运行时提示词同步校验通过。浏览器回归验证了真实按钮发起的请求携带原文、校正中断保留旧依据、完整新版与各轮历史的保存，以及编译恢复。构建仍报告现有的大包体提示。

自动测试验证程序传递、路由和版本行为，不证明模型的语义判断正确。真实 GLM/high 复测的产物与人工观察见[运行记录](/Users/chun/Downloads/uom-forge-evaluation/domsys/runs/20260928-151756-glm-high-source-review-r2/运行记录.md)；实验使用相同 Description 和上次保存的业务理解，补回完整原文，对旧设计重新审阅后独立重新建模。CSV 的 Classes/Associations、人工评价和旧设计的新审阅意见均不作为重新建模输入，实验在 JSON 编译前停止。

语义判断仍由 LLM 完成；“可表达”只表示报告明确范围内得到支持，不能视为整个业务已穷尽。旧项目缺失原文时也不能据此宣称完成原文覆盖检查。


### GLM/high 复测结论

- BTMS 一轮通过；HBMS 首轮“需修改”，Pi 修订后第二轮通过。两案均在 JSON 编译前结束，全部请求参数核验为 glm-5.3 / high。
- HBMS 补出了原预订/所选优惠与成交酒店之间的联系，实际修订了完成前提和偏好筛选，证明反馈驱动修订的路径能工作。
- 人工核查仍发现 BTMS 的“既有安排不取消”推断过强，以及 HBMS 的住宿日期、房型、间数、成交报价未充分承接。冻结旧稿复审也未稳定指出这些主要缺口。
- 因而本次实现和程序验证完成，但语义质量只部分达到预期；不能把两案的“可表达”结论写成主要缺口已解决。真实运行没有触发依据校正，该分流目前由自动化回归验证。
