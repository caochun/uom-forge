# 提示词整体审查（2026-09-27）

> 后续落实：本记录中的调整已落实到运行时提示词、编译修复、反馈入口说明和相关文档。以下保留修改前的审查结论，源码行号对应审查时的位置；最新完整内容见 [运行时提示词](运行时提示词-领域建模流程.md)，可用 `npm run docs:prompts -- --check` 校验同步。当前保持概念模型粒度，必要属性与输入语义保留在定义中。

审查以当前工作区代码为准，覆盖 01—08、两类失败修复、Pi 的系统提示词、检查工具描述和修订消息，也核对了实际传入材料、编译校验和澄清解析。以下是静态审查结论，没有调用真实 LLM 验证输出效果，本次没有修改运行时提示词。

整体方向已经符合此前讨论：业务理解整理原文，建模依据提出领域语义需求，模型设计建立语义底座，案例用来检查表达与推理能力，业务流程不成为模型元素。无需推倒重写，但仍有一些旧限制、职责越界和交接不一致。

**各阶段的职责**

| 阶段 | 应回答的问题 | 当前评价 |
| --- | --- | --- |
| 01 业务理解 | 原文说了什么，主体、条件、动作、结果和上下文是否清楚、一致？ | 职责明确，溯源符合目标；整理规则、理解检查和阅读方法存在重复。 |
| 02 建模依据 | 模型必须表达什么，智能体需要据此推理出什么？ | 定位正确；仍有过强的“明确提出”限制，以及解释、推导与假设混在一起的问题。 |
| 03 模型设计 | 用哪些对象、关系、操作、只读能力和规则表达这些语义？ | 元素职责基本清楚；计划如何转为必要语义、用户反馈能改变什么，还需明确。 |
| 04 设计表达检查 | 当前文字设计能否支持案例，修订是否破坏已有表达？ | 职责清楚；应与 06 一致区分案例输入、模型语义和预期结果。 |
| 05 JSON 编译 | 如何忠实地把已经完成的设计转换为结构化模型？ | 职责清楚；属性、输入被称为元数据并统一留空，语义保真要求不够明确。 |
| 05b 编译修复 | 如何修复结构或引用，同时保留设计语义？ | 目标正确；仍采用完整编译提示词加修复要求的旧写法。 |
| 06 独立业务案例检查 | 最终结构化模型能否支持案例？ | 已基本对齐方法；与 04 检查不同产物，保留二者有意义。 |
| 06b 报告修复 | 如何修复报告结构、引用和结论一致性？ | 职责明确，已无需重新扩写。 |
| 07 模型自述 | 仅凭模型，可以说明哪些业务含义和已声明边界？ | 找业务缺口的要求超出了它实际拥有的输入。 |
| 08 业务讨论 | 如何依据当前提供的材料回答用户问题？ | 大体合理，但包含已经不存在的界面操作指引。 |
| Pi 系统提示词与工具 | 如何输出完整设计、发起检查并有限次修订？ | 迭代职责基本明确；不必在这里再增加一套建模方法。 |

**优先修正的问题**

1. **02 仍把必要的业务含义和额外的生命周期假设一起限制了。**

   [prompts.ts:81](../server/stages/prompts.ts#L81) 仍要求“只有材料明确提出身份、多个实例共存、后续引用……才记录相应要求”，第 106 行又把“参与配对”列入不能补入的事项。而第 134 行已经改为“按业务含义确定必要的实例区分，不要求材料使用‘独立身份’等建模术语”。两阶段的判断口径不一致。

   例如，“每笔申请的审核结果归属于该申请”已经要求保持申请与结果的对应；不需要原文再写“独立身份”或“参与配对”。建议统一为：保留业务含义要求的实例区分、对应关系、状态变化和结果归属；不额外假定发生次数、历史追踪、保存期限或排他限制。材料明确区分模板与实例时仍应保留区别，但不必展开成生命周期清单。

2. **需要区分有依据的推导和需要用户裁决的解释。**

   [prompts.ts:80](../server/stages/prompts.ts#L80) 和第 103 行规定“解释……不能写成确定的模型要求”，第 91、97 行又强调材料没有明确的步骤不得补造。这些约束有助于防止虚构，但“解释”的范围过宽，会与 01 允许还原明确指代、省略，以及后续希望智能体推理计划的目标产生张力。

   建议明确：上下文唯一确定的含义、从已明确规则必然得出的结果可以保留，并说明推导依据；存在多个可能解释、需要增加业务前提才能成立的内容保留未决。不能增加业务活动或规则，不等于不能推导已有规则的后果。

3. **“不建流程”已经说清楚，但“从流程中提炼什么语义”还不够明确。**

   [methodology.ts:15](../server/stages/methodology.ts#L15) 说明计划顺序不成为流程、任务或编排元素，却没有明确区分业务强制依赖和某次办理安排。

   “审批通过后才能拨款”应保留为操作前提和规则；文档恰好先介绍查询客户、后介绍查看库存，并不自动形成强制顺序。建议增加这一正向原则：从已知计划中提炼必须成立的条件、业务变化、依赖和结果；仅用于叙述或示范的顺序保留在案例中。检查模型能否支持符合目标和约束的计划，不要求把所有叙述顺序固化为唯一执行路径。

4. **案例的初始事实、模型语义和预期结果应明确分工。**

   [methodology.ts:23](../server/stages/methodology.ts#L23) 已要求给出证据路径，[assessment.ts:26](../server/stages/assessment.ts#L26) 也明确建模依据不能替模型补缺失语义。这是正确的，但“证据只能来自当前模型”还应区分模型能力证据与案例输入。

   例如，案例可以给出“申请 A 当前已审批”作为初始事实；模型提供拨款的前提和效果；“可以拨款”是需要检验的结果。不能要求本体模型保存所有示例实例，也不能把案例里的预期步骤拿来补足模型缺少的规则。建议将这层分工和“模型自设边界不能豁免明确要求”统一放入 04、06 共用的检查方法。

5. **05 的“只做概念识别”遗留约束，存在丢失业务语义的风险。**

   [output-contract.ts:5](../server/stages/output-contract.ts#L5) 把 `properties`、`inputs` 和 `evidence` 一并称为“程序元数据”；[prompts.ts:178](../server/stages/prompts.ts#L178) 要求省略它们；[compiled-model.ts:34](../server/validation/compiled-model.ts#L34) 还会拒绝非空属性与输入。这不是仅靠换一句提示词就能完全改变的行为。

   不细化技术字段可以保留，但业务属性和输入语义并不是元数据。例如额度、有效期、计算范围和作用事项可能直接参与规则判断。最小调整是明确：当前不展开字段结构，但设计已经写出的必要属性、状态、输入和计算条件，必须完整保留在对应定义、前提或规则中；不能因数组留空而省略语义。是否启用结构化字段可以另行决定，不必为此扩展当前流程。

6. **用户反馈的语义权限没有完全说明，可能让设计与检查依据不一致。**

   [modeling.ts:26](../server/stages/modeling.ts#L26) 只从业务理解生成建模依据；[prompts.ts:126](../server/stages/prompts.ts#L126) 又让用户反馈用于修订设计。04 仍只把建模依据作为业务来源。反馈若只是指出模型缺口没有问题；反馈若修改了业务规则，设计和审阅者就可能按不同口径工作。

   建议保持简单：模型反馈只能在现有建模依据内指导表达调整；新增或修改业务事实、规则时，先保存到业务理解，再更新建模依据。不增加新的评审概念，但要让提示词与实际反馈入口遵守同一条规则。

**其他需要收敛的内容**

7. **03 的澄清要求过窄，输出格式又少了必要说明。**

   [prompts.ts:142](../server/stages/prompts.ts#L142) 要求至少存在两种受依据支持的解释。确实影响明确业务要求的缺失条件，不一定能列出两种已有解释，例如材料要求按额度分级却没有给出阈值。应允许指出这类必要信息缺口，同时继续排除无关细节和设想场景。

   另外，提示词只说“每个问题依次写”，但 [clarifications.ts:72](../shared/clarifications.ts#L72) 的解析实际要求编号列表，以及分行的“依据、歧义、影响”。应补足这句简短格式要求，避免有效问题未进入待确认列表；无需重建一套复杂输出协议。

8. **07 自述不应承担基于业务需求的缺口评估。**

   [narration.ts:13](../server/stages/narration.ts#L13) 要求“如果……无法推理出某类业务计划……请直接说明模型缺少什么”，但该调用只有模型，没有建模依据或指定案例。它可以复述已有语义、声明的边界和定义内部的歧义，不能自行选业务目标并判断该模型遗漏了要求。建议把基于需求的缺口判断留给 04、06。

9. **08 保留了失效的产品指引。**

   [discussion.ts:20](../server/stages/discussion.ts#L20) 仍让用户点击“按讨论调整模型”，当前界面中没有这个按钮。应删除该固定按钮指引；需要说明下一步时，区分业务说明更新与模型表达反馈，引用实际存在的操作。

10. **05b 可采用与 06b 相同的专用修复方式。**

    [modeling.ts:94](../server/stages/modeling.ts#L94) 仍重复整段编译提示词，再附校验错误和旧输出。它没有越权重新建模的问题，优先级低于语义问题；可以收敛为原设计、旧输出、错误、结构约定和保真要求，避免重复完整首次任务说明。

11. **还有不会进入 LLM 的旧内容，应与实际提示词问题分开看。**

    [methodology.ts:31](../server/stages/methodology.ts#L31) 的 `REPAIR_METHOD` 含有旧的 `repairTarget=model` 协议，但没有被导入使用，因此当前不影响模型调用。README 和部分界面仍使用“检验情形”，运行时已改为“业务案例”。这些应清理以免维护时重新引入，不能据此断言当前 LLM 仍在执行旧协议。

**建议保留并强化的建模方法**

业务理解还原原文语义并保留引用；建模依据提出必须表达的事实、约束，以及需要支持的业务情形；模型设计选择足够表达这些语义的对象、关系、操作、只读能力和规则。已知计划帮助识别必要语义，但不固化为流程元素。检查时，以案例的初始事实和目标为输入，只利用模型提供的语义说明能否得到预期结果；明确业务要求不能表达就是模型缺口，业务本身未确定就保留待确认边界。

下一轮应围绕上述原则删改现有句子，优先修正 02 的过强限制、03/04/06 的推理口径以及 05 的语义保真。01 和 06b 可基本保留；不需要增加阶段、元模型类型或长篇防错清单。
