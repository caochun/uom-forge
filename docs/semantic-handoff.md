# 业务理解与候选建模的语义交接

默认流程为：原始文档 → 业务理解 → 业务依据 → 模型设计 → 模型 JSON。前三份生成内容是供人阅读、供后续推理使用的文本；只有最后的模型 JSON 是必须通过程序验收的机器协议。

## 业务理解

direct 和 Pi 都只生成一次 Markdown 文档整理稿，回答“文档在说什么，是否说清楚、说一致了？”。沿用适合原文的组织方式，理顺层次、语句、条件和指代，指出术语不一致、前后矛盾及文字与公式不一致等表述问题。这里不专门提炼建模事实、故事或检验情形，也不要求固定章节。程序不因格式差异发起重试，也不自动调用独立核对或段落修复。

整理稿须忠于材料，完整保留适用范围、条件、例外、数字、单位、公式及不确定表述；不能仅输出摘要，不能通过默选解释或修正数值消除原文冲突。区分“表达不清”与“未曾涉及”，只对实质影响文档含义的问题请求确认。这些是阅读和审阅准则，不是格式闸门。

段落末尾的 `[[source:block-id]]` 可用于关联原文。程序按真实文档块保存引用快照；无法识别的引用不会被当成原文证据，也不阻断理解或建模。可识别的待确认问题进入回答表单，其他内容保留在正文。保存答案会修订当前整理稿并使旧业务依据和模型过期。

## 业务依据

一次调用从当前文档整理稿提炼事实、业务故事、规则和少量检验情形，直接输出 Markdown。不生成固定 facts/stories JSON，不要求事实类型枚举、稳定编号、步骤顺序字段或交叉引用协议，也不对中间内容做校验重试。

业务依据回答“有哪些事实和过程，未来的模型必须能够表达？”。从整理稿提炼角色、事项、联系、前提、变化、结果与归属，组织故事，实际列出明确规则的条件、例外、阈值、单位和公式，不能用“按文档规定”代替。它是完整的建模业务输入，不能只是一份有损摘要；整理稿和原文仍保留供人核对来源。

依据选择少量具体检验情形，交给设计与检查共同沿用；假设实例不是新增事实。未决边界继续保留，不补造次数、配对、追踪或排他要求。本阶段不决定对象拆分、合并或关系结构。它只收到整理稿，不声称核对过原文。

`businessBasis` 保存原始文本；`business-basis` SSE 事件标志本次文本已完整生成。`part: basis` 的正文增量直接展示在业务依据页，推理增量不混入正文。前端分别保存文本和完成标记，中断、保存和刷新都保留已收到内容。

## 模型设计

输入为本轮业务依据，以及迭代时的候选业务字段和设计反馈；不再同时传入完整整理稿。新的业务解释应先由用户保存到整理稿，再重新提炼依据。标题和组织方式可调整，不进行章节验收或提交工具交接。direct 仍一次生成设计；Pi 在模型设计阶段进行最多三轮语义迭代。

核心问题始终是：当前的对象、关系、业务操作、只读能力和规则，能不能表达一个具体的业务事实或业务过程？先尝试表达有依据的典型情形，发现真实缺口才调整，避免机械增加概念。

检查也要识别无依据的新增限制：不能在边界中声明某项业务未知，却又把一种假设写成确定的操作前提、次数限制或排他规则。末尾声明未知不能抵消定义中的确定假设，应去掉该限制或如实保留条件语义。

Pi 在正文生成一份完整设计，同轮调用无参数的 `check_expression`。工具自动读取正文，调用独立 LLM 审阅，使用与设计相同的业务依据，沿用其中的检验情形；必要时可从同一份依据补充关键情形。修订检查还收到上一版设计及先前反馈，核对是否丢失已有约束或归属，不能只相信修订说明。反馈要求具体情形、设计元素、表达路径及真实缺口。工具不要求事实、故事或设计 JSON，不重复传输设计参数。反馈发现具体缺口时，Pi 在原会话修订相关定义并再次调用工具；复查不能换掉失败例子。检查通过后直接结束，不增加 finish 或总结回合。

检查意见也是自由文本。首行的简短结论仅用于决定是否继续；无法识别时保留整份意见供人审阅，不重生成，也不宣称通过。若模型未调用工具，宿主直接检查已生成正文；有缺口再把反馈送回同一个 Pi Agent，避免专为工具交接增加调用。

最多三次设计生成和三次检查；设计与已检查版本相同则停止，不再重复审阅。业务待澄清、达到上限、检查服务失败或修订失败时保留完整设计和意见，继续编译；默认没有执行总时限，用户取消时停止任务，仍保留已生成草稿。实验可通过正数 `UOM_PI_TIMEOUT_MS` 显式设置总时限，`0` 表示不限制。截断的修订不会替换上一份完整设计。原始文档 blocks 不进入此 loop，业务未知不得由模型补造。

设计说明应明确对象边界、关系端点、状态变化、只读能力、规则及业务过程。未知业务含义保留为边界，不替用户选答案。可识别的澄清交回业务理解，按本轮业务依据核对引文并标注 `basisSource: business-basis`，不能冒充原文；旧设计的整理稿引文仍可识别。澄清元数据提取失败只留下提示，设计原文仍保留，不能因此触发重生成。保存答案后更新整理稿，再重新提炼依据和建模。

`design-review` 事件保存轮次、设计快照、检查意见及停止原因；`part: semantic` 流式展示设计，`part: design-check` 流式展示审阅意见。完整设计与正在生成的部分修订分开保存，刷新或停止后可审阅。`model-plan` 在编译前交接最终设计。建模页仍为业务依据、模型设计、模型视图三个步骤；检查与修订属于模型设计内部活动。未决意见标为待审阅，不把合法候选标为任务失败。旧结构化语义草稿及来源链仍可查看。

## 模型 JSON

编译只接收模型设计与紧凑结构说明，不再读取原始文档、业务依据全文、历史会话或专家模型。输出为对象、关系、操作、只读能力、规则与业务过程，保留设计中明确的边界。它是格式转换，不是再次业务建模。

编译提示词以“模型 JSON 编译器”为角色，不要求重新提炼事实、组织故事、选择检验情形或判断业务表达。提示词全文与各阶段职责对照见 [模型视图生成与阶段职责](model-compilation.md)。

程序验证 JSON 语法、必要字段、全局唯一 ID、关系端点及元素引用。可机械处理的围栏等包装先由解析器清理；固定空元数据按既有约定补齐。无法通过时最多请求一次完整 JSON 修复，反馈具体错误及上一轮响应，再由同一校验器验收。网络错误、取消或断流不触发格式重试，不使用 `validate_json` / `finish_json` 工具重复传输整份模型。

结构合法后发布 `model-checkpoint` 和最终结果。`designReview` 记录文本设计的表达审阅；`expressionReview.status = not-run` 表示没有另行运行旧版的编译后模型检查，两者不可混淆。设计审阅不证明编译绝对保真，结构通过也不能据此宣称业务正确或完整覆盖。

模型视图按 `part: compile` 分开展示思考增量与 JSON 正文。`timing.callId` 区分生成和修复调用，重试不拼接两份 JSON；通过 `model-checkpoint` 后才更新图形并收起生成记录。编译的部分输出随草稿保存，中断或刷新后标为未完成。上轮候选的独立检查面板改称“候选模型复核”，重新生成期间隐藏旧记录，避免与设计循环中的检查混淆。

编译失败不会清除业务依据、设计或上一版候选。前端可使用保存的设计单独重试编译；业务依据和设计审阅随请求及结果保留，但不重复进入编译提示词。新审阅同时绑定整理稿、业务依据（`businessBasisVersion`）和设计版本；任一不匹配就不把旧审阅附到新结果上。重试使用本轮保存的整理稿快照，避免新发现的待确认问题改变引用版本。旧审阅没有依据版本时沿用其原有版本约束。业务内容已变化时应重新建模。

## 独立审阅与历史兼容

Pi 从业务理解到最终模型，在首轮设计通过时需要五次调用：业务理解、业务依据、设计、表达检查、编译各一次。每轮实际语义修订增加设计和复查两次调用，最多三轮；最终 JSON 不合法时最多另加一次修复。direct 仍为四次基础调用。调用次数不等同于实际耗时承诺。

用户可在“检验模型”中单独运行模型自述和业务过程支撑评估。这两项只读取候选的业务语义，不依赖原文或前序说明替模型补全含义。

历史草稿中的结构化事实、故事、情形、映射和表达检查继续保留。已有候选的显式 verify/map 恢复入口仍支持原有版本校验和修正逻辑，但新建模不会自动进入这些调用。事实、故事和具体情形作为方法论继续体现在文本提示词中，不再要求每一步先通过程序协议才能继续。
