# 语义计划改造检查报告

## 检查结论

提示词和流程均已按“业务事实 → 业务故事 → 代表性情形 → 候选模型 → 表达检查 → 事实映射”的责任边界调整。核心判断贯穿理解、建模和验证：

> 当前的对象、关系、业务操作、只读能力和规则，能不能表达一个具体的业务事实或业务过程？

结构校验只负责 id、引用、类型和版本一致性，不把格式通过当成业务语义正确；业务理解缺口、模型缺口和用户待确认事项分别处理。

## 提示词检查

- 理解提示词要求区分原文事实、推断和未决边界，并保留参与者、重复发生、共同上下文、拟议/实际/临时结果。
- 独立理解核对双向检查原文遗漏、无依据新增和冲突，所有发现都保存原文块 id 或说明中的逐字片段。
- 事实提取提示词只允许引用业务说明片段；故事提示词只能引用事实 id；代表性情形绑定事实 id，明确不是新增事实。
- 建模提示词要求先用代表性情形检验表达，只在具体事实无法表达、情形无法区分或模型矛盾时调整；不要求对象、关系或规则清单齐全。
- 首次表达检查和修正后复查都使用程序冻结的情形。模型只返回 judgments，程序保留事实、依据和情形，避免模型通过改写情形制造“通过”。
- 修正提示词只允许处理 `repairTarget=model` 的缺陷；理解问题回到业务理解，业务歧义进入澄清。
- 映射提示词禁止使用故事/情形 id 代替事实 id，只接受当前候选中真实存在且类型一致的元素。

## 流程检查

- 每个事实、故事、候选、表达检查和映射结果都通过 SSE 发布，并写入草稿。
- 理解核对结果、业务依据、建模说明、候选和检查快照带有版本关联；业务依据或候选变化会使下游结果失效。
- 候选修正每轮保存快照和变更记录；后续复查发生回归时回到前一份候选。
- 检查中断可单独恢复当前候选；映射中断可单独重试，不会重新编译建模说明。
- 手工修改候选后必须重新检查才能重新映射；恢复使用保存的建模依据，不把后来追加的问题目录当成新的业务版本。
- 前端将事实、故事、模型设计、候选模型、表达检查和事实覆盖映射分别显示为进度项，并把可恢复动作路由到对应阶段。
