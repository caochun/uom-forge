# 业务理解与候选建模的语义交接

第一阶段解释业务，第二阶段决定如何表达为模型。规范与业务领域无关，不包含样例业务的预设对象或规则。第一阶段输出 Markdown，不生成模型字段表，也不生成额外的结构化阅读提纲。

## 第一阶段的 11 项判断

| 要回答的问题 | 对应章节 |
| --- | --- |
| 业务主体是谁？ | 业务主体与业务事项 |
| 主体提出或处理什么事项？ | 业务主体与业务事项 |
| 哪些东西具有独立身份，可以长期管理和重复引用？ | 可持续管理的资源和业务产出 |
| 哪些只是属性、状态、指标、阈值或计算结果？ | 业务输入、判断规则与计算依据、临时计算结果 |
| 哪些业务产出需要记录或追踪？ | 可持续管理的资源和业务产出 |
| 对象间有哪些明确的业务联系？ | 业务事实与对象联系 |
| 哪些联系来自临时计算？ | 临时计算结果 |
| 哪些行为会创建记录或改变状态？ | 业务过程与状态变化 |
| 哪些行为只是查询、计算、校核或评估？ | 业务过程与状态变化 |
| 哪些分支属于同一概念的类型差异？ | 业务主体与业务事项 |
| 哪些为材料明确、上下文推断或尚未说明？ | 对应段落标明，不确定事项汇总 |

固定章节为：业务概述、业务输入、业务主体与业务事项、可持续管理的资源和业务产出、业务事实与对象联系、业务过程与状态变化、判断规则与计算依据、临时计算结果、不确定事项。无材料依据时写“材料未说明”，不能为了补齐标题而编造内容。章节检查只能发现缺项，不能代替语义审查。

需要用户作答时另附“待确认问题”，编号列出。有限选项在下一行以“选项：…”或“多选：…”提供，使用分号分隔；其他问题使用文字回答。保存答案会将确认说明并入当前业务理解，更新对应的不确定表述；只回答部分问题时，其余问题仍待确认。原始说明及完整问题目录保存在本地，用于修改、撤回和恢复，不作为额外依据传给后续阶段。

## 原文引用与说明来源

业务理解输入携带原始文档块 id。模型在有依据的说明段落、列表条目或表格行末尾输出 `[[source:块id]]`，可用逗号引用多个块。程序只接受实际存在的块 id，原文内容由程序复制并保存快照；引用标记移出正文，作为理解结果的 `sources` 元数据经 SSE 和结果响应交给前端。

业务事实的 `source` 是业务说明摘录，不是原始文档。前端按本轮建模保存的业务说明及引用快照，显示“文档块 → 业务说明 → 事实 → 模型元素”的来源链。第二阶段仍只接收业务说明正文，原文快照不作为额外业务输入进入编译或评估。用户确认、手工修订以及无引用的旧结果明确区分；引用缺失不阻断流程。引用只能建立可追溯关系，不能替代语义审阅或证明全部业务覆盖。

## 第二阶段语义准备：事实与业务故事

direct 和 Pi 使用同一条固定准备链。第一次结构化调用从业务说明中提取最小业务事实，每条记录稳定 id、事实类型、参与主体、涉及对象、条件、结果、确定性及业务说明中的逐字依据。第二次结构化调用只使用已经校验的事实，将其组织为带目标和有序步骤的业务故事；故事与步骤都必须引用真实 fact id，不得补造新事实。

自然语言判断由模型完成。程序负责 JSON 结构、枚举、唯一 id、原句存在性、步骤顺序和跨记录引用。事实和故事分别通过 `semantic-plan` SSE 事件发布并写入草稿；原始 JSON 增量不进入建模说明正文。语义计划带版本和 `facts`、`stories`、`mapped` 三种进度状态，取消或后续阶段失败时保留最后一个有效快照。

## 第二阶段 A：建模判断

输入包含业务说明以及已经校验的事实和业务故事，迭代时增加当前候选模型的业务字段和用户反馈。旧模型里的引文、来源字段、界面状态不进入提示词。没有业务说明时不能启动建模。

输出 Markdown 建模说明，明确对象边界、关系方向和上下文、业务操作的目标与效果、只读能力及其输出、规则、业务过程及“建模判断与边界”。概念存在不依赖业务过程已开展。临时结果不默认独立建模；如说明明确要求保存和独立追踪，也不能仅凭“结果”一词禁止成为对象。本轮不细化属性。

已确认的业务说明属于当前理解，必须落实为模型的业务语义，不能重复列为未决问题。业务过程应明确目标、要求、适用分支及过程复用，使模型本身足以作为后续检验的输入。

“材料未说明”不等于必须让用户回答。合理的设计取舍应解释理由；算法、字段、实现方式和范围之外的功能不自动成为待办问题。只有业务理解中存在无法合理判断的歧义，且不同答案会改变本轮模型时，才增加可选的“需要补充的业务信息”章节，每个编号条目必须说明依据、歧义和模型影响。依据摘录当前业务理解的原句，歧义写出不同解释，影响写出不同解释各自改变什么；优先提供选择答案。不设固定数量，无必要问题则省略整节。

这些澄清是审阅信息，统一并入业务理解的问题目录；已确认或尚待回答的同一问题不重复添加。模型保留尚未确定的语义边界，不自行选定答案。用户可以先审阅候选，再回到业务理解确认；保存答案会修订业务说明并使旧模型失效。

每个可选澄清分别校验格式、重复和引文。无效条目不进入问题目录，也不作为已确认事实；结果与前端提示说明原因，完整 A 输出仍保留。其他有效问题正常交回业务理解；已有模型说明继续进入 B，B 不接收任何澄清条目。若 A 只有问卷而没有模型正文，则仍然失败，不能生成一个空模型冒充完成。这个隔离机制只处理审阅元数据，不放宽候选模型、引用或证据校验，也不解决或抹去模型中真实的未决边界。

## 第二阶段 B：模型整理

新的一次模型调用接收 A 的模型说明正文、已校验的事实与业务故事，以及紧凑的输出结构要求；不继承 A 的会话历史，也不重新读取原始文档。A 的可选澄清章节由程序提取并交回业务理解，不让 B 新增问题。完整 Schema 只用于程序校验，不展开到提示词。不改变 A 中作出的建模决定，将它们整理为 object、relation、action、function、rule 和 activity；建模判断及边界进入 boundaries，并保留在相关定义的描述中。

本地校验 JSON 结构、全局 id、关系端点、目标及规则和活动引用。错误直接反馈，不静默删掉引用或补造对象。模型元素的直接 evidence 仍为空；间接来源通过本轮保存的业务说明引用、业务事实及事实映射追溯，不把这一链路等同于已验证的原文完整覆盖。

A 的说明在 B 启动前发布给前端。B 失败或被停止，不抹掉 A 的说明，也不覆盖已有图模型。格式正确不代表与 A 完全语义等价，仍需结合模型自述和后续支撑评估审阅。

前端可以单独重试 B，传入已保存的完整建模说明、语义计划和当前业务理解。B 的模型调用收到建模说明及已校验语义计划；当前业务理解还用于重新核查事实原句、澄清依据和整理后的业务表达检查。若用户已经改动业务理解、问题答案或建模反馈，说明对应的版本已过期，应重新建模，不能把旧说明的整理结果视为最新模型。

## 第二阶段内部：业务表达检查与定点修正

```text
当前业务理解 → 事实 → 业务故事 → A 建模判断 → B 模型整理与结构校验
       ↓                                      ↓
       └────────────── 业务表达检查 ────────────┘
                              ↓ 有明确的模型缺陷
                        局部修正与校验
                              ↓
                        原有用例与相关语义复查
                              ↓
                    事实映射到最终候选元素
```

检查器是新的独立调用，只接收当前业务理解和实际候选模型，不接收 A 的自我解释、原文、对话历史或专家参考模型。它从业务说明中选取重要事实和区别，用具体情形检验：能否确定实际参与对象和同一事项的上下文，能否区分有业务差别的情况，是否混淆已有事实、拟议安排、临时结果和实际变更，是否遗漏关键规则条件。并非只遍历候选已有的概念。

每个用例保留业务事实、业务说明中的原文文字依据、具体情形、实际元素引用、判断理由、差异及建议。依据直接保存原文片段并校验其确实出现在业务说明中，不依赖段落编号、块 ID 或位置标识。判断为“可以表达”“模型待修正”或“业务尚未明确”。接受描述、规则和关系组合的等价表达，不要求与某份参考模型同名，也不把未细化属性或未实现算法当成缺陷。引用存在不等于解释正确，仍需审阅检查者的业务判断。

结构化调用请求 JSON 输出。检查元数据允许机械规范化：重复引用去重、唯一且完全一致的元素名称解析为 id、未提供的可选澄清列表置空；无法唯一解析的引用仍失败，不模糊猜测目标。可引用已有模型级 `summary`、`boundaries`，它们不是新增本体概念。可选澄清逐项验证，无效项留下警示而不作用户问题，也不抹掉其他有效检查。

最多进行一次自动修正，只处理说明中有明确依据的模型缺陷。修正调用返回按元素更新的补丁，不重新生成整个模型；每项修改必须关联缺陷用例并说明原因。程序只补充固定的空证据、空属性、空输入及待评估标记，业务语义字段必须由补丁完整提供。程序原子应用补丁，检查整个模型的结构、唯一标识和引用；任一错误就保留原候选。业务歧义不能据此自动选答案，必要的新问题继续走业务理解的确认表单。

修正后再次独立检查，程序固定原有用例的 id、事实、依据段落和情形，模型只返回对应的 `judgments`，无需再次抄写用例；包含之前通过的用例，可另列新用例。遗漏、弱化用例或引用不存在元素使复查无效。业务歧义没有新的用户答案就不能因“模型写了待确认”变成已解决，程序保留其未决状态。如果原先可以表达的事实退化，自动恢复初始候选，修正尝试和复查结果仍可审阅。到一轮预算后即停止，不以增加循环掩盖剩余问题。

B 结构校验完成和每次修正后都会发送 `model-checkpoint`。草稿保留初始候选、修正候选、两次检查、补丁原因及剩余事项。取消、检查失败或超时不会清除最后一次有效候选，也不会标记为通过；刷新页面将未完成的运行标记为中断。没有完成复查的修正候选仍可查看，状态明确为“检查未完成”。手工编辑或修改业务理解后，旧检查不再代表当前模型。

前端在候选页增加可展开的“业务表达检查”，优先展示剩余事项、修正内容和模型元素入口，不增加主页面、不展示原始 JSON 流。初始建模说明继续保留，经过修正后提示以模型视图的最新定义为准。每次调用都有独立耗时：通常 A/B 加一次检查，有缺陷才增加修正和复查。检查全部通过只说明本轮用例可表达，不证明业务完整覆盖。

表达检查和可能的修正完成后，独立结构化调用把每个事实映射到最终候选中的对象、关系、操作、只读能力、规则或过程。程序拒绝不存在的元素 id、错误类型、重复映射和缺少覆盖结论的事实。映射失败不抹掉已验证候选、事实和故事，而是在草稿中保留未完成状态及警告；单独重试 B 时重新生成映射。

## 模型自述与业务过程支撑评估

这两步都只读取候选模型的业务语义，不带入文档、业务理解、用户答案、旧引文或上轮评估。自述复述模型表达的业务；支撑评估检查模型中的对象、关系、操作、只读能力和规则能否有效支撑模型声明的业务过程、目标和要求。

评估必须覆盖全部已声明过程及其要求，引用真实模型元素解释支撑方式，指出内部缺口或矛盾。模型已表达的业务分支和规则直接作为依据；不能因为没有原文或确认记录而重新发问。此评估不检查业务理解是否全部进入了模型；第二阶段的表达检查负责用业务事实对照候选。两者都不能替代用户对原文理解和完整性的审阅，构造阶段的检查元数据不传入最终评估。

缺少关系、操作或规则时直接给出模型修改建议。只有模型内部缺少业务事实、且不能作出合理判断时，才提出带模型依据、歧义、影响和选择项的 clarifications，由前端放回同一张业务理解表单。评估不接收业务理解、独立答案或历史问题来完成这一判断。
